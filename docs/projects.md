## Workspace index and project isolation

Workspace Index: Scan `.tex`, `.ltx`, `.bib`, `.bst`, `.sty`, `.cls`, `.def`, `.clo`, `.fd`, `.ldf`, and `.bbx`, `.cbx`, `.lbx`, `.dbx` from biblatex; tracks file changes and gives priority to unsaved content in the editor.

Font definition `.fd` and Babel language support `.ldf` files also participate in scanning, monitoring, recorder input tracking and log positioning, and explicit input provides path completion, navigation and safe renaming. The native engine gives priority to reading the accurate `.fd` / `.ldf` files, completing the reserved suffix and checking the actual target.

biblatex style, language, and data model files provide notation and editing capabilities as LaTeX source code. Explicit `\input{local.bbx}`, `\InputIfFileExists{local.dbx}{...}{...}`, and other calls support path completion, dependency navigation, and file renaming; completion preserves these suffixes and dependencies continue to distinguish independent projects. The lookup follows native engine rules, e.g. when `local.bbx.tex` is present, it takes precedence over `local.bbx`; candidates are also checked against the final load target. No dependencies are inferred here from biblatex's `style=`, `citestyle=` or data model options.

Data and code file dependencies: Compile recorder actually reads CSV, TSV, DAT, JSON, XML, YAML, YML, and TXT, as well as common code, profile participation content snapshots, expired PDF checks, SyncTeX checksums, and compilation cancellation, including shared input outside the workspace. The listening extension is not case-sensitive; files read only as data do not enter the LaTeX symbol index, and explicit source code inclusions such as `\\input{notes.txt}` are still indexed normally. The image/data type of the symbolic link alias will still be retained after normalization. When the target has no extension or uses a suffix such as `.tex`, content changes can also be tracked and the difference between the data and the source code index can be maintained.

Jump, hover, completion, signature help and renaming will use the dependencies of the main document to distinguish independent papers and avoid the interference of tags, documents, macros or environments with the same name in other projects. Newly created root documents that have not yet been written to disk also participate in symbol scope and meaning checking of shared inputs. The reference query and renaming of a shared definition will cover all projects that use it, and the renaming will also check for conflicts in these projects; if the reference in the shared source code points to different definitions in different projects, lacks a corresponding definition, or becomes a common parameter in a certain project, renaming will be rejected. Draft buffers that are not yet associated with the main document continue to use the workspace scope; automatic compilation entries still follow the disk root file rules below.

Redefinition of string test commands is propagated in file loading order; when shared parameters have different interpretations, only the affected name editing is restricted. For details, see [Cross-file context of string tests](string-test-projects.md). For the success and failure hooks and sub-file reading order of static file checking, see [Conditional File Hooks](conditional-string-tests.md).

The input files and image paths in the shared source code are also parsed separately for each main document, and the compilation input check uses the current compilation context. No single jump is provided when the root is not unique and the same parameter points to different files; path completion searches these main document directories. File movement requires that the path edits of all users are consistent. If they are consistent, they will be merged into one edit; if there is a conflict or a project cannot resolve the path, rewriting will be refused.

The parsing type of source code, literature database, and literature style is determined based on the input command and the path actually read by the tool. The extension of the symbolic link target will not change the purpose. For example, when `refs.bib` points to `.payload`, `.tex` or `.png` files, it still provides citation key completion, jump and cross-file renaming. When `alias.sty` points to `.bib`, it still parses the LaTeX commands in it; the style file does not generate literature entries. Opening, editing, closing, reloading, and file moves retain confirmed usage, and current static declarations or new tool records can update usage while preserving unsaved text. External databases discovered by the bibliography tool respect the source code index scope, and static bibliography sources participate in content verification of old PDFs even if they do not have a bibliography log.

The maximum disk index is 1024 files, a single file is 2 MiB, and the directory depth is 16, skipping hidden directories, build directories, and directory symbolic links; files actively opened by the editor are not subject to disk file size restrictions. File references with relative paths also load dependencies outside the root directory recursively up to 16 levels. Clients that support dynamic file monitoring will automatically register for monitoring; other clients need to send `workspace/didChangeWatchedFiles` to update disk changes of unopened files.

## Root file identification

Automatic root file identification only considers the `.tex` / `.ltx` main document that can still be compiled on the disk, excluding document classes and document environment tags that are converted from confirmed primitives into text; the same rule is also used for the compilation entry of shared sub-files. The underlying root document is retained when primitive meaning or input source cannot be confirmed, and explicit root configuration and magic annotations retain precedence. It is also rechecked if the file has been deleted but the notification has not yet arrived. Document examples in packages, document classes, and support files will not form additional compilation roots. When compiling from these files, the corresponding main documents will be used. Explicit root configurations, magic annotations, and errors in direct compilation of deleted main files will continue to be retained, and other projects will not be silently used.

Relative `build.rootFile` can point to the main document outside the workspace. The configured root URI returned by the compile event can be directly used for status query, cancellation or compilation again. The relative configuration will not be interpreted again according to the directory where the root file is located; it is compatible with overlapping workspace folders. Preserve missing errors after deleting the root file to avoid misuse of files with the same name in other directories.

The root file priority is: configured `rootFile` → `% !TeX root = ../main.tex` instructions in the first 20 lines of the file (supports chain parsing and checks for loops) → the only main document containing the current subfile → the current `.tex` file. When there are multiple main documents, you need to specify the root file explicitly.

Declaring `documentclass`, `begin` in the target or copy source does not serve as a main document tag; for example, `\let\saved\begin{document}` does not make the example file a compilation root file. `meaning` When viewing tags, confirm the meaning of the primitive according to the project context. For details, see [meaning operand](meaning.md).

## Path analysis and completion

- Document link: input file, library, local package/document class, picture and `\url` / `\href`; the four-parameter `\hyperref{URL}{category}{name}{text}` will append the `#category.name` target according to the actual PDF link, retain URL escapes and existing fragments, and skip targets that require macro expansion. Input files, libraries and local packages/classes are first searched in the compilation main documentation, and then the current documentation is tried; pictures are searched according to the `\graphicspath` rule below. `% !TeX root` is always relative to the document in which it is declared.

File path completion will search the main documentation and the current documentation at the same time, giving priority to the main documentation for compilation, which is consistent with TeX when reading files with the same name, supporting relative parent directories and subdirectories; processing extensions according to the load command, retaining other items in the document list, and existing slashes after the directory. The URL parameters of `\url` / `\href` are parsed independently, allowing `%20` and other encodings, and the text in the URL is not regarded as a LaTeX command.

Commas in single file parameters belong to paths: `\includegraphics{images,one/plot,one.pdf}`, `\include{chapter,one}`, `\subfile{chapter,one}` and `\addbibresource{refs,one.bib}` continue to complete the full file name after the comma. List parameters such as `\bibliography`, `\usepackage` and `\includeonly` still only complete the current entry, retaining other names and delimiters.

`\includeonly{chapter-a, chapter-b}` supports list path completion, jump and file/directory renaming, retaining other list items and blanks; compilation selections are maintained simultaneously when renaming selected chapters. This command only selects the declared chapters of `\include` and does not create separate input dependencies. For the impact of chapter selection on cross-file string semantics and renaming, see [Chapter Selection Instructions](selected-string-tests.md).

## Input and code files

- Static `\csuse{input/include}`, literal `\csname input/include\endcsname` and pure aliases also participate in source code dependency discovery, file linking, definition jumping and cross-file environment matching. Definitions loaded in the source code can be indexed before the first compilation. Aliases provided by local packages and nested inputs are parsed according to each main document; inputs used as macro arguments or in the body of unexecuted definitions do not establish indirect dependencies. The filenames of these calls also provide path completion, supporting unclosed grouping, comments around filenames, directory suffixes, and ungrouped or quoted spaces and Unicode names. Completion resolves aliases according to the selected main document. When no main document is selected, each item must have the same meaning for the call. File renaming retains the calling form and comments. When the ungrouped `input` file name is changed to a name containing spaces, curly braces are added, and the semantics of the original file name terminating blanks are retained. `include` retains extension restrictions; inconsistent edits are rejected when the meaning of the shared location is inconsistent. Dynamic names, arbitrary macro expansions, and dependency graphs that cannot be stably determined are not inferred.

The static file function of `include` only recognizes the grouped file parameters immediately following the command, allowing spaces and comments in between. It does not accept text groupings after asterisks or optional descriptions as file dependencies, jump targets, rename paths, or missing file conditions; file renaming does not thereby modify the normal text displayed in the PDF.

Path navigation, completion and file renaming of input, file inspection, chapter selection, bibliography, package/class loading and its option forwarding commands check whether the command still retains the built-in meaning and whether the call is consumed as an argument by a user macro. Confirmed `detokenize` ends the actual parameters after a complete group; subsequent real file commands continue to support navigation and renaming, and the file names in the display group remain intact, and are compatible with static naming calls and pure aliases. Conservative argument bounds are maintained when encountering delayed redefinition or unidentified sources of code input. File names displayed as ordinary text are not automatically rewritten; static file paths that can be confirmed in the macro definition body are still involved in file and directory renaming, and the paths for future calls are retained.

Static project dependencies exclude inputs, references, packages, and classload commands explicitly converted to literals by unredefined `detokenize`, `string`, and `meaning`: these paths will not require saving, nor will macros or reference entries for the corresponding files be mixed into the current project. Comments at file parameter boundaries are parsed and processed according to existing file names; dynamic list items, names split by comments, or sources that cannot be confirmed continue to be conservatively retained. The compilation validity check also excludes references, packages, and class loading commands that are converted from confirmed primitives into text to avoid mistakenly marking the PDF as expired when unread candidate files appear; the actual called macro text, parameter forwarding, and the situation where the meaning of the primitive cannot be confirmed still retain candidate path monitoring. User macros may execute their own arguments and therefore continue to retain their underlying source dependencies; real input and recorder-acknowledged dynamic sources in the deferred macro body also retain dependencies and save checks. Dynamic sources, internal LaTeX input commands that have not yet been parsed for static images, unresolved named calls, delayed or argument sources with unconfirmed execution semantics, re-word segmentation and code reading, delayed command rebinding, original conservative processing when the analysis exceeds the boundary or the meaning is unstable.

`\input` can complete the above TeX source types. When `.tex` is omitted, the common abbreviation is retained and other extensions are written explicitly; jumps also obey the rule of only automatically inferring `.tex`. The main document can use the `.tex` or `.ltx` extension. The input path follows TeX's default extension search order, for example, when `chapter.ltx` and `chapter.ltx.tex` coexist, the latter takes precedence. `\include` and the chapter selection list are added to `.tex` according to LaTeX rules, and will not mistakenly point to files with the same name without extension or `.ltx` files; for example, `\include{chapter.ltx}` corresponds to `chapter.ltx.tex`.

Input file renaming will also check the entire batch of moved `\input` targets, including files moved in and out in the same batch. When the source with the same name in the new root directory blocks the original document relative fallback path, use the clear root relative path; after changing to an extension such as `.ltx`, the same name `.ltx.tex` will still be read first, and editing will be refused if the target cannot be maintained through the path. Naked filenames, quoted paths, spaces, and Chinese paths obey the same checks.

`\input` supports curly braces, bare file names and double-quoted file names, such as `\input chapter.tex` and `\input "my file"`; these forms are involved in completion, jump, project dependency and file renaming. The naked file name ends with a blank; curly braces are automatically added when renaming, completing or quick fixing introduces spaces, and existing ASCII double-quoted paths are retained. When the bare file name or double-quoted path is changed to a non-ASCII name such as Chinese, it will be uniformly converted into curly bracket form to ensure that both pdfLaTeX and XeLaTeX can read the target file. File names containing macro expansion, comment splicing, or mixed quotes are left to be discovered by the compiled recorder.

The static file name of `\InputIfFileExists{file}{before input}{if missing}` also supports path completion, jump, project dependency and file renaming, using the same search order and extension rules as `\input`. Symbols in files can be navigated across files and renamed before compilation; path editing preserves two code parameters, comments and whitespace, allowing Chinese, spaces and comma file names. Command completion and signature help indicate that the second parameter is executed before the file is read, and the third parameter is only executed if the file is missing. Missing files continue to be compiled according to the LaTeX branch; the server does not simulate branch execution, and static dependency analysis does not treat `\IfFileExists`, which only checks for existence, as a file input command.

Static named calls and pure aliases `InputIfFileExists` and `IfFileExists` also support path completion, navigation and versioned files and directory renaming, retaining comments, suffixes and two code branches around the file name. The former uses actual existing files as project sources, while the latter only records file references; missing candidates of both are involved in compilation condition tracking, and when files are replenished during compilation, the old branch results will be marked as expired. Dynamic names, redefinitions, unexecuted macro bodies or uncertain project meanings continue to be conservatively rolled back and the two branches are not evaluated.

`\IfFileExists{file}{if exists}{if missing}`'s file names support path completion, jump and file renaming, and can check TeX sources, images, data files and files without extensions. The editor retains two branches. The search and batch file move checks comply with TeX's suffix search order; renaming does not turn the file existence check into a file read, nor does it add the symbols in the checked file to the static scope of the main document. Command completion and signature help distinguish between existing and missing branches.

`\lstinputlisting[options]{file}` supports code file path completion, file linking, definition jump and versioned file/directory renaming, accepts any suffix and non-suffix files, and retains Chinese characters, spaces, commas and comments around calls. Select files according to the main documentation and LaTeX's `.tex` priority/original name fallback rules. Static dependency analysis does not import this path into the symbol index as LaTeX source code. Command snippets and signature help follow the calling form of an optional parameter that does not accept asterisks. Currently, static editing supports default search and recognized literal format options; `inputpath`, `style`, macro values, unknown options, and in-project command redefinition will skip path inference to avoid modifying wrong files. The resolved static code path captures a snapshot of the contents of the data input before first compilation, including unknown suffixes, no suffixes, and aliases pointing to `.tex`; changes will invalidate build results, old PDFs, and SyncTeX. Candidate file creation and alias changes also participate in build checks. The `.tex` sample displayed after compilation will not bring its labels, input commands, or `listings` settings into the main document scope; the same file will still retain source code usage when it is explicitly `\input` read in other projects. Calls that cannot be resolved statically continue to rely on common input formats confirmed by the recorder. When the compiler confirms that the code file is missing, the server combines the actual reading prompts and source code echo to locate the error to the file name parameter and provides bounded spelling repair. Fixes preserve full suffixes, options, comments and line breaks, use versioned editing and check TeX suffix masking; macro expansion, indeterminate context and custom search settings do not provide guesswork fixes.

`\verbatiminput{file}` and `\verbatiminput*{file}` (`verbatim` package) also support path completion, linking, definition jumps and versioned file/directory renaming of any type of file. Asterisks can be separated by spaces; this command has no optional parameters. Search according to the main documentation and the `.tex` priority rule. The code file participates in the first build snapshot, PDF content history and SyncTeX failure check. The LaTeX commands in it are not executed or indexed as the project source code. The search settings for `listings` and the redefinition check for `verbatiminput` are independent of each other; static path inference is skipped when the search rule cannot be confirmed. When the package outputs a missing file prompt, the server combines the confirmed log file context and source code literal path to give warnings and bounded spelling repairs within the file name range, and retains the successful compilation status. Long filename wrapping, asterisks, comments, CRLF, and versioned editing are all supported; ordinary missing auxiliary files, dynamic paths, and command redefinitions do not generate guesswork path fixes.

`\VerbatimInput[options]{file}` (`fancyvrb`) also supports completion, linking, definition jumps, versioned file and directory renaming, and static input tracking, accepting one-time optional arguments and asterisks that can be left blank. The default search respects the main documentation and the `.tex` precedence rule. The double-quoted path and the file name in the literal `\detokenize` package can also be edited; quotes are automatically retained or added when spaces are introduced when completing or renaming, and `\detokenize` is used when introducing non-ASCII names so that they can be read by pdfLaTeX and XeLaTeX. Known literal format options and `commandchars=none` can be statically analyzed; `commandchars` of executable code, unknown options, macro values, command customization and related redefinition will skip inference to avoid mistaking the actual execution content as display data. Configuration checks for the three types of code input are independent of each other. `\LVerbatimInput` and `\BVerbatimInput` of the same family use the same path, completion, signature help, renaming, input tracking and missing file repair rules, retaining their respective typeset forms. The three commands share settings and internal customization checks; the shortened error echo must locate a unique call in the entire command family.

Code files can also be read with `\inputminted[options]{language}{file}`, which supports path completion, jump, file movement, building data snapshots and missing file repair. Filename wrapping, global setting checks and static boundaries are detailed in [minted code](minted.md).

## Document library, package and document class

- TeX comments in the package list will be preserved: dependency tracking, linking, path completion and file/directory renaming of `usepackage`, `RequirePackage` and `RequirePackageWithOptions` only use real names; confirmed missing package errors are located to specific names and spelling fixes are provided. Optional arguments end at the first unprotected brace `]`, `WithOptions` does not accept preceding options. Names that are dynamic, nested, or spliced from annotations are not inferred; error location and repair require that the entire list be static names.

- Document class names are processed as a single file, and comments before and after the `documentclass`, `LoadClass` and `LoadClassWithOptions` names are supported. Navigation, completion, file/directory renaming, missing class error locating and spelling fixes Preserve spaces and commas in names and share the first unprotected `]` boundary with signature help; do not split class names as package lists, nor change class names containing spaces to another compact name.

- BibTeX style paths support TeX comments before and after the name. Navigation, path completion and file/directory renaming only modify the real name, retaining comments and CRLF. `bibliographystyle` is processed as a single file name, and commas in the name are supported; the indentation at the beginning of the line after comments is ignored according to TeX rules, and ordinary leading and trailing blanks, blank lines, dynamic macros, and names spliced by comments are not statically inferred.

- `\nobibliography{databases}` supports comma-separated library paths, signature help, path completion, navigation, dependency tracking and file renaming; retain list-separated whitespace and extension writing, ignore TeX whitespace in the path according to BibTeX rules and complete `.bib`. `\nobibliography*` without parameters will not treat subsequent groups as bibliographies, nor will optional specifications be accepted.

- The library lists of `bibliography` and `nobibliography` also recognize TeX comments before and after the file name; commas and curly braces in the comments do not participate in file name parsing, and file/directory renaming and path completion retain comments and CRLF. Linking and editing are only provided within the actual file name range, and file names appearing in comments are not used as dependencies or rename targets; dynamic macros, nested groups, and non-consecutive file names spliced by comments are not statically inferred.

`\bibliography` and `\bibliographystyle` complement `.bib` and `.bst` respectively, and are reserved if the same suffix already exists; for example, `\bibliography{refs.ltx}` reads `refs.ltx.bib`, but `refs.ltx` with the same name will not be read. When the library is used through `\bibliography`, the name must retain the `.bib` suffix. `\addbibresource` Continue to use explicit resource paths.

LaTeX removes spaces, tabs, and newlines before writing the database name of `\bibliography`, so `\bibliography{my refs}` actually reads `myrefs.bib`; whitespace in directories and extensions is also handled by this rule. Navigation, dependencies, and renaming will select the file actually read and ignore interfering files with the same name that contain spaces. The explicit file name for `\addbibresource` continues to be blank.

`\bibliographystyle` will preserve whitespace in the name, while BibTeX will reject such auxiliary file directives, including leading and trailing whitespace in the name. The server does not parse it into a loadable style, completion excludes unrepresentable filenames, and renaming refuses to introduce such paths; compilation still reports tool-generated errors.

Package and document class parameters are loading names, `\usepackage` / `\RequirePackage` always append `.sty`, `\documentclass` / `\LoadClass` always append `.cls`; for example, `\usepackage{local.sty}` search `local.sty.sty`. Completion and renaming will remove the last suffix appended by the loader to the target file to avoid duplicate extensions; jumps follow the same rules as dependency tracking, and files with the same name without extensions will be skipped. File move also checks that these references remain selected to the intended target after the bulk move.

`\RequirePackageWithOptions` / `\LoadClassWithOptions` follows the same search rules and supports local file dependencies, completion, jumps, missing file repair and file renaming; the former also recognizes package lists. Command and signature completion includes `\RequirePackage`, `\LoadClass`, and both forwarding commands. The normal loader accepts `[options]{name}[minimum version]`, the forward command accepts `{name}[minimum version]`, and options for the current package/class are forwarded by LaTeX; the server does not incorrectly suggest explicit option arguments before forwarding the command.

The second parameter of `\PassOptionsToPackage{options}{name}` / `\PassOptionsToClass{options}{name}` supports local file completion, jump and safe renaming. When moving a package or document class, update the option forwarding declaration and the actual loading command synchronously, retaining the option content, comments, and line breaks to avoid compilation still succeeding but the option becoming invalid. Option forwarding of static naming calls and pure aliases also supports path completion, jump and file renaming of the second parameter, and the name change is synchronized with the actual loading target; only the forwarding option still does not import the target source code. The alias must be specified in the scope of the current main document. Macro actual parameters, unexecuted text and cross-project meaning conflicts will not be inferred. The forwarding option alone does not add static input dependencies to files; these names are processed as option table keys, and no path inference is performed for internal or trailing whitespace, macro expansion, and unresolved targets. The command snippet and signature help contain two required parameters.

LaTeX ignores spaces, tabs, and newlines in package and document class load names, such as `\usepackage{my local}` load `mylocal.sty`. Find, completion, diagnostics, and rename follow the same rules; a disk file with the same name with spaces will not be treated as the source from which the name is actually loaded, nor will unsafe path updates be generated for it.

Path completion will match the entered blanks according to the loading rules, and supports cross-line packages, document classes and `\bibliography` names, including directory fragments; after accepting the completion, you can still jump to the file actually read by the compiler. Directories with spaces that are not available for these loaders do not appear in the candidates, `\input` and `\addbibresource` continue to retain available space paths. `\bibliographystyle` When the parameter already has a blank, path completion that leaves invalid blanks is not provided.

Static named calls and pure aliases of `bibliography`, `nobibliography`, `bibliographystyle` also participate in library and style dependency discovery, path completion, jump and file renaming, retaining lists, comments and explicit suffixes. Document libraries and styles are loaded according to their respective data types, and the content is not declared as a LaTeX macro; missing candidates participate in file condition checking before compilation, and editing of shared files requires that the meanings of each main document are consistent.

Static named calling and pure alias `includeonly` support chapter path completion, jump and file and directory renaming, retaining selection lists, comments and explicit `.tex` suffixes. Chapter renaming will update the indirect selection list synchronously to avoid missing the selected chapter after recompiling; the names in the list are only used as file references, and the chapter declaration will not be loaded separately. When the meaning of the shared source is inconsistent, the call is in an unexecuted macro parameter or macro body, the command is redefined or the name is dynamic, the corresponding static file editing is not provided.

The local `.bst` style participates in path completion, jump, file movement and compilation input checking through `bibliographystyle`; modifications need to be saved first, and changes during compilation will cause the results to expire. The style error reported by BibTeX will be located at the corresponding line of `.bst`; it will not be parsed as LaTeX syntax when editing.
