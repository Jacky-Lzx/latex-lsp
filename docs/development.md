## Build checks and tests

The VS Code client lives in [`editors/vscode/`](../editors/vscode/README.md), with its own npm lockfile, TypeScript build, and VSIX packaging workflow. `npm test` connects to the Rust server from a real VS Code Extension Host, using isolated settings and projects to validate language features, builds, and restarts. See the extension README for development and runtime requirements. Editor adapters belong in that directory; editor-independent features remain in the Rust server.

```sh
cargo fmt --all -- --check
cargo clippy --locked --all-targets -- -D warnings
cargo test --locked
```

When running tests on macOS, you can use `TMPDIR=/private/tmp cargo test --locked` to avoid the `/var` and `/private/var` aliases of the system temporary directory from making the file URI inconsistent with the canonical path.

Incremental compilation is turned on by default for development and test builds, and the cache is reused to speed up repeated compilation after modifying the code; debugging information is still turned off by default. Incremental caching will increase disk usage. You can set `CARGO_INCREMENTAL=0` when you need to save space. When source code level debugging is required, `CARGO_PROFILE_DEV_DEBUG=2` or `CARGO_PROFILE_TEST_DEBUG=2` can be set as needed; release builds continue to use independent configurations.

During continuous development, you can use `cargo clean --locked -p texquill --profile dev --dry-run` to preview the usage of debug products in this package. After confirming that there are no tests or builds running, remove `--dry-run` for cleaning. This will allow the next development/testing to rebuild this package, retaining the dependency cache, release products, and measurement files in `target/benchmarks`. Do not run builds or cleanups during benchmark measurements.

Tests include UTF-16/incremental editing, syntax tolerance, cross-file navigation, bibliography completion, synchronization of disk and unsaved contents, and stdio protocol flow to initiate real-process verification.

Performance measurement uses [continuous editing benchmark](benchmarks.md), which plays back incremental editing on the release process, and counts the end-to-end delay under each language function and input burst.

`tests/language_ids.rs` Regression with stdio covering unnamed documents, editor language type, priority of project input roles, and parser lifecycle when incrementally editing, moving, closing, and reopening.

For external tool installation requirements and various test commands, see [Real Tool Regression](testing.md).

## Parsing scope

The server uses static analysis and does not execute arbitrary TeX macro expansion. It indexes distribution filenames with kpsewhich and ls-R, and uses curated package metadata for command documentation. Formatting calls tex-fmt by default, or optionally latexindent. PDF previews and mathematical semantic checking are outside the server; rename and fixes reject ambiguous edits.

## Module directory and dependency conventions

The source code is classified into directories according to responsibilities, and each directory declares the module it belongs to through `mod.rs`:

Shared subprocess tasks, process group cancellation and bounded output reading are located inside `process/` for compilation, formatting, ChkTeX and distribution discovery.

| Directory | Responsibilities |
| --- | --- |
| [`server/`](../src/server/mod.rs) | `Backend`, LSP request processing, ordered message dispatch, build coordination and result delivery |
| [`config/`](../src/config/mod.rs) | Server configuration, project overrides, and latexmk configuration discovery |
| [`project/`](../src/project/mod.rs) | Document workspace, project discovery, input and resource paths, TeX distribution and package metadata |
| [`parser/`](../src/parser/mod.rs) | LaTeX/BibTeX syntax, token boundaries and FancyVerb, listings, minted readers |
| [`symbols/`](../src/symbols/mod.rs) | Declaration and reference namespace, macro meaning, scope and static execution context |
| [`bibliography/`](../src/bibliography/mod.rs) | Bibliographic databases, citations, partitions, contexts, and BibTeX/Biber log diagnostics |
| [`language/`](../src/language/mod.rs) | Completion, navigation, symbol renaming, signature help, folding, highlighting, semantic tokens and function caching |
| [`editing/`](../src/editing/mod.rs) | File moving and renaming, refactoring, code actions and quick fixes |
| [`formatting/`](../src/formatting/mod.rs) | Document, range, and on-type formatting for LaTeX/BibTeX |
| [`diagnostics/`](../src/diagnostics/mod.rs) | Source code diagnostics, ChkTeX and diagnostic reports delivered according to client capabilities |
| [`compilation/`](../src/compilation/mod.rs) | Build execution, bibliography and index tools, logs, artifacts, source snapshots, and SyncTeX |

[`lib.rs`](../src/lib.rs) only declares the subsystem; [`main.rs`](../src/main.rs) is responsible for the stdio service startup and transmission life cycle; [`text.rs`](../src/text.rs) retains common text locations and editing tools. LSP protocol processing is concentrated in [`server/backend.rs`](../src/server/backend.rs), and the specific functions are implemented by the subsystem to which it belongs.

References use the actual owning path, such as `crate::project::workspace::Workspace` and `crate::bibliography::citations`. New modules should be registered in the corresponding directory. Internal modules use `pub(crate)` or narrower visibility by default. External callers and integration tests use the subsystem paths to which `texquill::project::workspace`, `texquill::language::features`, `texquill::compilation::build` and `texquill::server::Backend` belong. The root module no longer re-exports these modules or entries.

Module unit tests move with their implementations. Integration test entry points and shared fixtures retain their layout in `tests/`, so existing `cargo test --test <name>` commands remain valid. Bibliography log parser submodules remain in `bibliography/bib_diagnostics/`, with caching and source validation managed by the parent module.

## Code structure and analysis cache

[`analysis.rs`](../src/analysis.rs)'s `AnalysisContext` explicitly holds the symbol/source map cache, file watch and cancel signals for each sync analysis. The entry creates the context within the worker thread; nested analysis uses independent caching, inherits observers and cancellation signals, and restores the outer layer when it ends normally or abnormally. The old synchronous reader accesses the current context through the unique scope adaptation bridge, and each subsystem no longer maintains thread-local caches separately. Context cannot span asynchronous suspension points, nor is it reused across requests; source dependency graphs check cancellation at pass boundaries.

[`compilation/build/execution.rs`](../src/compilation/build/execution.rs) only executes the tool and returns `Outcome`; [`server/builds/`](../src/server/builds/mod.rs) builds a queue within the management connection, and `completion.rs` verifies, submits the workspace results and sends notifications. The original public paths such as `compilation::build::BuildManager` remain compatible with export, and the actual paths are used internally. TeX and bibliography tool logs are implemented separately in `compilation/build_log/`, and the existing public parsing entrance remains unchanged.

Shared command semantics are classified into [`symbols/commands/`](../src/symbols/commands/mod.rs): the built-in parameter directory, declaration reading and meaning analysis are maintained separately; hook parameter analysis and declaration documents are also classified into `symbols`. Parsing, item discovery, and symbol querying directly rely on these semantic modules. `language/signature.rs` is responsible for LSP signature help, active parameter positions and completion snippet generation, and is no longer used as the command analysis entry for other subsystems.

The runtime workspace is uniformly read and written through [`project/store.rs`](../src/project/store.rs). The first time a write lock is mutably accessed, the independent revision number is advanced; replacing the entire workspace does not reset the revision. The diagnostic publisher consumes only that revision and no longer owns the version of the analysis input. Client capabilities and project build observations are assigned to `ClientCapabilities` and `ProjectState` of [`project/state.rs`](../src/project/state.rs) respectively. Standalone tests can still build workspaces directly; updates to services and build coordinators go through `WorkspaceStore::write`.

Workspace snapshots share immutable document revisions through [`project/documents.rs`](../src/project/documents.rs); when modifying existing documents, copy-on-write is used, and text updates replace the corresponding revisions. The distribution file index also shares storage. Snapshots still copy document mappings and project status, but they no longer copy the text, syntax, and distribution index of unchanged documents. Context refresh first compares existing analyzes and then modifies documents that have indeed changed.

Push diagnostics are calculated in the background on separate workspace snapshots, and consecutive edits within 75 ms are combined into one batch. Edits, file events, configuration, and build updates invalidate old snapshots; expired results are no longer published. Diagnostic calculations do not hold workspace locks or occupy the serial execution location of ordinary LSP messages.

The pull diagnostic queries the bounded cache before analysis. The results are simultaneously bound to the workspace revision number and the actual read disk path status analyzed, including missing files, project configurations, latexmk configurations and auxiliary files; when these inputs have not changed, full or unchanged can be returned directly. There is a budget for the number of file observations and cached bytes, and will be reanalyzed when the limit is exceeded. If the diagnostic content and document version are not changed in delayed file notification, the original resultId will still be retained.

Language queries and pull diagnostics capture independent workspace snapshots in message order, and no workspace read locks are held during background calculations; canceled background tasks do not block editing or saving. Language analysis has four dedicated worker slots. A slot remains held until its computation finishes; cancelling a request does not prematurely release a slot still in use. Queries that generate renames, file moves, and on-type formatting edits check the workspace revision before returning, and return ContentModified when the source code revision changes; when only the background metadata changes and all source code revisions are the same, the latest snapshot is used to recalculate. Imperative code operations preserve message order position until the client confirms applyEdit, preventing subsequent document notifications from overriding unconfirmed edits. Requests waiting for the diagnostic cache do not occupy the parallel quota for interactive requests. Completion, diagnostics, navigation, reference, rename, hover and signature help reuse up to four source code dependency graphs and 16 sets of dependency traversal results in a single query, and are cleared when the query is completed. Save notifications request the full text to align that document's snapshot before compilation, while preserving other documents' unsaved contents and the existing build checks.

[`symbols/query_cache.rs`](../src/symbols/query_cache.rs) Establish symbol analysis cache for references, renames, rename pre-checks and diagnostics, and also create source code map caches. There are a maximum of four results in each of the three types of results: named reference, label declaration, and project command signature, sharing an estimated budget of 8 MiB. Exceeding the limit is only calculated without caching; the key includes the workspace identity and the original query document/exact project scope. Nested queries have independent caches. The outer cache will be restored when it ends normally or abnormally. The cache will be cleared after the query ends. Completion, definition, and hover also build symbol analysis and source map caching, reusing the same order of LaTeX source signatures by workspace and precise project scope; signature help uses source map cache. Explicitly passed resource contexts in document partitions do not use the normal named reference cache.

When the client supports diagnostic refresh, the queued analysis that has been replaced by the new revision returns the standard `ServerCancelled`, and the service merges and refreshes the latest version to avoid repeated recalculation after old diagnoses are backlogged.

Compilation allows for CRLF/LF and trailing newline differences between the editor and the file, and retains a fingerprint of the actual disk bytes to check for file changes during compilation; extra whitespace lines and other content modifications still participate in save verification.

The current job `run.xml` control file explicitly written in the recorder is not used as user XML input; ordinary XML data still participates in verification. `staleReason` for out-of-date compilation results gives changed input or file conditions.

The string conditional context is analyzed by document reuse source code. The cache key includes resource reading rules, inherited macro meanings, calling parameter syntax and hook aliases. Each document retains up to two interpretations and shares a process-level estimated byte budget; it is parsed normally but not cached when the limit is exceeded. Cross-file traversal still checks the current meaning, rebuilding the grammar and clearing the semantic token and symbol cache only when the final context of the document changes.

The completion provider applies the candidate budget of `completionLimit + 1` after prefix filtering and deduplication, and stops constructing entries after the normal candidate reaches the budget. Document search first retains the candidate with the highest score and name ranking before creating an entry; path completion bounded retains the current best candidate, continues to check subsequent paths, and maintains the existing ordering of directories, local files, and distribution files. The LSP layer continues to intercept the configured number and retains the incomplete list contract when the upper limit is reached.

[`symbols/extra_symbols.rs`](../src/symbols/extra_symbols.rs) Provide independent namespace, project scope and rename conflict checking for terms, indexes and expl3. [`symbols/expl3.rs`](../src/symbols/expl3.rs) Handle syntax patterns and full names separately to avoid changing the control word rules of normal LaTeX. Symbolic results are cached per Document and expire when the text or parsing context changes; semantic tokens are additionally subject to a process-level token budget. [`editing/refactor.rs`](../src/editing/refactor.rs) Provides conservative text reconstruction and batch fixes to exclude conflicting edits, old client commands will recalculate operations.

[`parser/minted.rs`](../src/parser/minted.rs) Share the header and original code boundaries of `mintinline` / `mint`, and read the normal options, language parameters and fvextra's verbatim parameters respectively. The pretokenization context in the macro parameters shares `InlineTokenization` with listings. Common tokens and groups are read through `syntax::tokenized_code_end`. Ordinary source code still uses the original character rules of fvextra. Languages and codes register opaque scopes in the main syntax scan, retaining command and executable header options; semantic highlighting, navigation, and renaming read the same scope. The third argument of `inputminted` is read through the file parameter entry, wrapped using unquoted file names for Python strings, and shares edit dispatch, project data roles, and build snapshots with FancyVerb through `code_inputs`. minted's setting check is independent of listings, reusing FancyVerb's global execution setting protection; missing file errors in native and fallback modes share precise source code echo checking and versioned spelling repair.

The minted environment reads the options and language using normal TeX rules before calling FancyVerb's shared end-of-text scanner from the next line; it cannot simply search for the end-of-string from the beginning of the entire header. The syntax layer continues to divide the discarded tail of the real end tag and the end line into two opaque ranges, so that folding and environment name linkage editing retain accurate boundaries, and the sample commands at the end do not participate in dependency and symbol processing.

The environment end scanner of [`parser/listings.rs`](../src/parser/listings.rs) first reads the options and name token once, and then determines the starting point of the text. Name is the active line wrap immediately to the next line; other tokens or groupings cause the scanner to discard the remainder of the header line. The whitespace and comment skipping logic under active line wrapping is located at [`parser/syntax.rs`](../src/parser/syntax.rs) and is shared by listings and FancyVerb. Only the exact closing string in the text ends with `lstlisting`, and normal parsing continues at the end of the line after closing. The original opacity range still starts after the environment name parameter, allowing editing functions to share boundaries without rescanning the header.

`lstinline` retains the call in the ordinary command index, and uses [`parser/listings.rs`](../src/parser/listings.rs) to read ordinary options and verbatim code boundaries; options continue to be scanned normally, with only delimiters and codes registering opaque ranges. The asterisk is read as a delimiter, and the brace form in ordinary text terminates with the first literal right brace; in the absence of a terminator, it is retained to the end of the line. The pretokenization judgment of macro parameters reuses the known parameter syntax and definition text range of `CommandSignatures`, and queries the first text position after the separator instead of the control word or separator to avoid mistaking the call that only the header is consumed as the pretokenization body; the pretokenization body uses ordinary grouping and token delimiter scanning, and supports comment continuation, nested grouping and cross-line.

The lexical context caches the parsed parameter syntax and incrementally scans preorder calls, caching the pretokenized scope using the actual end position returned by the parameter reader; normal outer scopes do not inherit this state. Inline command aliases first record candidate forwarding edges according to the new declaration increment, and only parse and confirm the current meaning when the name is reachable by the built-in inline reader; the syntax index retains the original call name, and the code and language parameters are registered in the opaque range according to the actual reader. Candidate cycles, unknown sources, parametric substitutions, and ambiguities do not establish verbatim meaning. The stable parameter syntax of the copy macro is only parsed in the inline lexical context and does not change the navigation's judgment of the macro's meaning; the copy source must have no repeated declarations and has been defined before copying, and pure static forwarding retains late binding behavior. The parameter reader additionally returns the reading progress of unfinished groups, for lexical context recovery only; navigation and editing continue to require complete parameters. The parameter header of the native `def` is read separately from the complete definition, and the declaration control words consumed as macro parameters are excluded in the calling order to avoid mistaking ordinary groups as replacement text. Semantic highlighting uses the call index directly, and only the native `verb` needs to restore the macro token from before the verbatim range. Completion uses the same code reader to determine whether there is already text, avoiding repeated insertion of code snippets.

FancyVerb's `Verb` direct call reads the header in the same lexical branch as the proven static alias, retaining the original call name and determining the actual reader before normal symbol and file operation indexing. It shares pretokenization context and token delimiter scanning, but the control words in the collected text will be executed; only the opening and closing delimiters are registered as opaque ranges, and ordinary scanning of the text is retained. Direct source code and saved forms continue to register the complete verbatim range, and retain line endings when the closing character is missing. The header and body boundaries are shared by `fancyvrb::InlineHeader`. After redefinition, the built-in text and saved name reading rules are no longer applied. `InlineContext` loads a verbatim reader that distinguishes fvextra / minted according to the current file package indexed, reusing the text boundaries of minted; `fvset`, `fvinlineset` and call-level `extra` Read in coverage order, settings are saved and restored with curly braces, explicit grouping, and static direct environment calls, and dynamic Boolean conservation preserves code isolation. The environment frame record name is restored according to the recovery rules of the existing environment diagnostics at the end; unexpected right curly braces do not pop up the environment frame. The verbatim environment is skipped entirely, and frames that require its skipped close command to be popped are not pushed. `VerbHeader` distinguishes header blank reads by collected parameters or direct source characters, first proving the pretokenization status of the text position, and then selecting the actual header; recording the delimited token that fvextra has pre-read when there are no optional parameters, so that the original FancyVerb reader also retains other character categories of the token. `EscVerb` and static aliases read the escaped body before the ordinary index, the header shares the asterisk and a single optional parameter reader, and comments are distinguished by pretokenized context and ordinary reading after the option; the body reuses the ordinary balanced data parameter reader, and unclosed curly brace diagnostics are retained. The completion reuse header and saved name reader determine that there are already parameters; signature help are only for commands with saved name ranges that pass through the data range, and comments and verbatim text within the name continue to reject prompts.

fvextra's `VerbatimWrite` and `VerbatimBuffer` reuse FancyVerb's environment reader with no required arguments and do not add non-existent asterisk forms; table of contents, prompts, folding and end mark linkage editing share this category. `VerbEnv` uses a separate single-line text reader to distinguish active header newlines, original code lines and strict closing lines; returns the true closing position and the consumed boundary on error. Syntax scanning restores the normal source code and unclosed environment scope after an error. The project environment index also checks the closure certificate to avoid mismatching the same name string at the end of the code line as the environment end. The environment header prompt reuses minted's language parameter endpoint, FancyVerb's header endpoint, listings' options endpoint, and the universal signature parameter reader. Only the immediate `begin` to which the actual verbatim range belongs can temporarily pass through the range in a header query, and comments are checked individually according to TeX escaping and wrapping rules; no syntax index or verbatim range is modified. FancyVerb's text scan and prompt share options, required tokens, and active newline boundaries. When a newline is actually consumed as a name token, the prompt range stops before the newline. Hints for listings only override public options; name tokens and discarded line endings continue to remain opaque. Complete or incomplete headers are supported, and body queries continue along the original verbatim rejection path. Check the command, environment declaration, undefinition, FancyVerb environment customization and `lstnewenvironment` of the current project in the request to avoid incorrect use of the built-in parameter list after redefinition.

[`bibliography/bib_diagnostics/biber_cycles.rs`](../src/bibliography/bib_diagnostics/biber_cycles.rs) Parse two circular inheritance templates of ordinary and XDATA. The log loop only copies the valid input set for the current template that is clear and unambiguous before logging the fatal level; the diagnostic query consumes this local source, `Sources::record`, still marks the current error and subsequent history as invalid, and does not expand the whitelist of recoverable errors. Positional queries reuse source, citation keys and relational field cache, normal loops mark unique `crossref` targets, XDATA only uses entry keys for compatibility with field-level loops; relative positions are bounded and deduplicated.

[`bibliography/bib_diagnostics/biber_aliases.rs`](../src/bibliography/bib_diagnostics/biber_aliases.rs) Only three types of complete native IDS conflict messages are parsed. Sources are selected by the complete previous input of the log, and the alias cache converts UTF-16 one at a time along the declaration order, saving canonical aliases, shared ownership keys, and up to 16 candidates per alias, while counting them separately to preserve ambiguity after limits are exceeded. The unique skipped alias must also check the cross-database uniqueness of the real primary key it belongs to; the duplicate alias message clearly indicates the accepted key and cannot be regarded as a skipped key. The main scope and related scopes share static indexes. When there is no source file name, the declaration is not guessed based on the message order.

[`bibliography/bib_aliases.rs`](../src/bibliography/bib_aliases.rs) Jointly traverse types, fields, complete entries and primary keys in source code order, and establish aliases and outer value indexes for the unique static `ids` field; field names use the ASCII case matching of the native reader. Aliases are stored separately, only the document declaration iterator of the editing function merges them, and the compilation log and database key cache continue to read only the actual entry headers. Independent alias renaming reuses the existing project scope and conflict check, and the double quote list is merged from the reserved value range into one curly brace edit; the semantic declaration and selection range use the same index, and the text is not rescanned.

[`bibliography/bib_completion.rs`](../src/bibliography/bib_completion.rs) Generate completions, snippets and hover descriptions from entry types, field names and input gaps recorded by the document parser, retaining existing field values and comments; custom types inherit bullet ranges. The type index also saves the key range of common entries, allowing compile diagnostics to locate the corresponding type name from the key row.

[`bibliography/bib_symbols.rs`](../src/bibliography/bib_symbols.rs) Use the complete construction range of the type index and the assignment range of the fields to create a document outline, retaining the selection range of key names and field names. Fields are traversed once in source code order and classified into corresponding entries; unfinished text also uses the current parsing scope, and the complete constructed index required for folding remains independent. The static alias directly reads `bibliography_aliases`, adds the corresponding field with the key symbol, and converts UTF-16 once along the source code sequence to avoid repeatedly scanning the prefix in a single-line long list. Tile symbols use the immediate parent symbol as a container, and the workspace search collects entries, aliases, and string symbols, excluding attributes.

Citation keys use independent static validation rules, allowing literal double quotes and parentheses; this rule is shared by declarations, ordinary and structured references, semantic tokens, compilation warning location, and spelling repair. When inserting a key containing double quotes into a double-quoted relationship field, the delimiter character that converts the entire value is completed. Renaming first merges replacements everywhere in the value, and then generates a curly brace value editor to avoid overlapping ranges caused by duplicate list keys.

The selection range reuses the boundaries of citation keys, label parameters, and BibTeX relation values. The structured reference uses the parameter role of [`bibliography/citations.rs`](../src/bibliography/citations.rs) to establish each parameter and the complete calling range. The end position of the command takes the last actual parameter to avoid swallowing the lookahead token used for compilation warning positioning. When the ordinary line range intersects with the structure range, the line candidate is skipped to prevent the last line of text from covering cross-line calls; the CR at the end of the comment is excluded before output to ensure that the LSP coordinates can be read back to the source code.

The expression scan of [`bibliography/bib_strings.rs`](../src/bibliography/bib_strings.rs) also records the selection range: single operand, literal value inside and outside, complete expression and assignment. Unclosed literals are preserved to the end of the current input, including whitespace; valid abbreviation references and compile-fix available declarations still follow the original independent verification. The editors chose to reuse the complete parsing scope of ordinary entries and special constructs, and limit the general group scan to each literal operand to avoid cross-grouping of square brackets or comment content with different values.

[`bibliography/bib_links.rs`](../src/bibliography/bib_links.rs) Reuse the document field parser to build URL/DOI link index, and uniformly handle literal escaping, URI encoding and repeated fields. Document linking and semantic highlighting read the same index, and incremental updates have the goal of not retaining old fields.

[`bibliography/bib_strings.rs`](../src/bibliography/bib_strings.rs) Recognize abbreviations in `@string` and value expressions, distinguish between literal text, numbers, comments and `#` operands; completion, symbols and semantic highlighting share this index, navigation and rename reuse project scope and shared reference checking. Real BibTeX regression validation preserves output across database expressions, preambles, and self-referential renames.

BibTeX semantic highlighting reuses type, field and expression indexes, additionally records numeric and operator ranges, and does not infer token types from the selection range. The original six legend indexes remain stable, with `property`, `number` and `operator` appended to the end. Literal contexts have lower priority than citation keys and exact links; annotations are logged by entry boundary scans, which protect quoted keys and percent signs within literals, and override candidates with the highest priority.

Entry types, field names, and string abbreviations share BibTeX identifier boundaries and first character checking. Legal colons, dollar signs, backslashes, and non-ASCII bytes do not truncate fields, nor block metadata, relational references, or string reference indexes for following fields; fields that begin with a number still stop parsing as invalid input.

[`bibliography/bib_completion.rs`](../src/bibliography/bib_completion.rs) Supplement custom candidates from assigned field indexes within the project scope, reading the current document first to preserve local spelling; standard fields take precedence over case-insensitive names. The other assigned fields of the current entry form an exclusion set, which can still complete itself when editing the current name. Fragment escaping of names shared by type templates and field templates, existing assignments and plain text clients directly insert literal names.

[`bibliography/bib_diagnostics.rs`](../src/bibliography/bib_diagnostics.rs) Handle undefined abbreviations, undefined entry types and duplicate entry diagnostics for BibTeX, sharing a bounded source parsing cache. The abbreviation fix saves content proofs in log reading order, only recommends previously valid database declarations, and reviews content proofs, compilation snapshots and versions; month edit completions will not be treated as loaded style macros. Duplicate entries reuse the citation key index to mark the precise range and associate the positions of previous entries with the same name in reading order. The level parsing of Biber record headers is shared by [`compilation/recorder.rs`](../src/compilation/recorder.rs). Both diagnostics and database role discovery check the actual level and skip pseudo records in the body.

Normal style warning and Biber entry messages also look up citation keys through this cache. Each source maintains a mapping of original keys to byte ranges, and duplicate keys are marked with explicit ambiguity; all different candidate files are checked against each other at query time, and uniqueness is inferred after skipping unreadable input. Confirmed key ranges directly generate document diagnostics, avoiding the need to enter general TeX line diagnostic parsing. Explicit filenames and individual line numbers have unchanged precedence, and cache is not preserved across logs.

[`bibliography/bib_diagnostics/biber_keys.rs`](../src/bibliography/bib_diagnostics/biber_keys.rs) Recognize case messages and duplicate key warnings between Biber database keys, using fully quoted filenames and case-sensitive key indexes to locate primary keys. The independent history only records the databases actually read before, and stops cross-database association after encountering syntax or unknown errors, missing sources, truncation, or the 1024 input limit; current explicit files can still be located. Source parsing reuses a single file of 2 MiB and a cumulative cache of 16 MiB, with up to 16 relevant locations. It does not guess the primary key across databases, nor does it infer that two keys should be merged. Duplicate keys reuse the same source and position logic: the relevant key is the same as the primary key, the unique primary position is not listed repeatedly, and all ambiguous positions are retained as bounded candidates; two native log formats are supported, skipping duplicates by default and retaining duplicates.

Biber citation key locations are lazily cached by source: one conversion to UTF-16 along the order of declaration in the source code, saving first line fallback ranges and up to 16 ranges per canonical equivalent, case-sensitive key. Biber-specific `key_name` uses NFD, shares with field diagnostics, and does not change the original key index of normal BibTeX navigation; canonical equivalence declarations share candidate upper bounds. The unique primary position is confirmed by only one range in the candidate table, and ambiguity is retained when the combination/decomposition form collides; related queries reuse the position table to avoid repeated scanning caused by a large number of the same long row entries. The cache belongs to the parsing source of the current log. The file and accumulated bytes continue to use the existing limits. Each message continues to check the trust status of the current source history.

The dynamic document collection reuses the two-parameter boundary of [`bibliography/citations.rs`](../src/bibliography/citations.rs), recording the `SetKey` and `Keys` roles respectively; member references follow the structured reference index. When both parameters are complete, the static collection key is added to LaTeX's document declaration index, sharing existing navigation, project isolation and conflict checking with handwritten documents, database keys and aliases. Signature and member completion read the same parameter role, and the first parameter will not be referenced as a member or already has key completion. The declared semantic tokens, symbols and selection ranges are reused in the document declaration, and no new dynamic collection namespace is created. The normal mode Biber test fixture is located at `tests/support/biber.rs`.

Partition projects with resource selections are additionally documented by `bib_section_keys::SourceTrace` for bounded numeric partition execution, static collection declarations and explicit/wildcard requests, and `bib_source_sections` certified read-only targets; resource collections share storage but do not replace numeric partition identities. The first explicit request locks a database entry, and the unlocked name assumes the final collection declaration for that partition. Source code/database bytes, execution work, and cross-root storage are respectively limited, and repeated executions are also included in the budget. Undocumented execution of generated code, source code collections, and handwritten documentation for database prefaces may not fall back to resource unions or partial citation/renaming results.


`entrydata` uses the `EntryData` parameter style to record a single `Keys` and `Code(0)` respectively. Asterisks are supported but optional descriptions are not accepted. `key_spans` shares single-key comment boundaries and static verification to prevent the comma list from being split into references; complete the name range and blank deletion range outside comments through the same actual parameter role, and continue to use single-line main editing and additional editing.
