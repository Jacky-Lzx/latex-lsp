# Build inputs and stale results

[Documentation](README.md) · [Build guide](build.md) · [Projects and Files](projects.md)

Project dependencies need to be saved before compilation; when input changes during compilation, the server discards out-of-date diagnostics. The following describes input sources, cancellation rules and validation checks for existing PDF/SyncTeX.

## Input and product verification

The code files actually read by tools such as `listings` are also involved in compilation dependency verification, including Rust, Python, C/C++, Java, JavaScript/TypeScript, Go, Shell, C#, Lua, R, Julia, Kotlin, Swift, Scala, SQL, Fortran and common web file suffixes, as well as `.toml`, `.ini`, `.cfg`, `.conf`, `.md`, `.rst` configuration or documentation. Only reads confirmed by recorder are adopted, and dependencies are not imported just because these files exist in the directory. Texts such as `\label` in the code will not become LaTeX symbols; explicit source code inclusions such as `\input{definitions.rs}` still support navigation and renaming. Even if the code content remains unchanged in size and modification time, it will invalidate the old PDF and SyncTeX and require recompilation.

Update detection for PDF, `.fls` recorder, and `.blg` document logs simultaneously compares content fingerprints with file metadata. When the compilation tool preserves the output size and modification time, the actual rewritten PDF is still recognized as a new product, and the new recorder input and literature warnings are read normally; this is suitable for file copying or custom compilation drivers that preserve timestamps.

The existing `.log` is retained before compilation, and the content fingerprint and file metadata are used to determine whether the log has been updated. When latexmk explicitly reports `Nothing to do`, it continues to read the last TeX log, so continuous compilation still retains the specific error location, alarm, page number and result analysis; after correcting the source code, the new log shall prevail. Startup failure, timeout, cancellation or unconfirmed reuse tool failure will not treat the unupdated old log as this diagnostics.

When opening a project that already has a compiled product for the first time, if the input is known to be newer than the PDF, latexmk with default parameters will automatically add `-g` to compile once to establish the input history of the PDF to avoid falsely reporting that the product is out of date just by resaving the same content. Subsequent saves with unchanged content still allow incremental compilation; customized `arguments` or `rebuildArguments` maintains the original calling method.

When the tool returns success but does not update the PDF, the server checks the modification time of the known input: if the source is newer than the old PDF or has been deleted, the product is reported as expired and the old PDF is retained on disk; no-op compilation can succeed where the product is still valid. When there is a recorder record, priority is given to checking according to the record, and the document source check is retained; unrecorded documents outside the selected chapter will not lead to false reports of expired products. Some TeX versions also record existence checks for files outside the selected chapter, and these files will still be conservatively checked. Images also participate in compilation-time changes, out-of-date PDF and SyncTeX checks; binary content does not enter the text index. Tools that do not generate recorders use image paths that can currently be statically parsed.

When the final log clearly reports `No pages of output.` or `warning (pdf backend): no pages of output.` corresponding to LuaTeX, even if the compiler exit code is `0` and the output directory retains the old PDF, the result this time is still `error`, and clears `pdfUri`, `pages` and `pdfSize`. The old PDF remains on disk and the server does not delete it. When there are no pages in the early rounds and a PDF is generated in the final round, the final successful result will continue to be returned; when subsequent unobserved log rounds may overwrite the report, the PDF will not be rejected based on this, and the original product validity check will still be performed.

The server also retains a content fingerprint of the generated PDF. After a PDF is overwritten by an external tool or failed compilation, even if the size and modification time remain unchanged, SyncTeX and subsequent compilations that do not rewrite the PDF will require recompilation; PDFs with only modified modification time and unchanged content are still valid. Successful no-op compilation retains the actual input range corresponding to the old PDF, and the old source will not be forgotten due to this recorder change. This history is updated only after the new PDF is actually generated.

The PDF history also records the content and missing status of `.synctex.gz` and `.synctex`. When a mapping is overwritten, deleted, or a mapping in another format later appears, bidirectional queries require recompilation; substitutions of retained size and modification time are also recognized, and timestamp adjustments with unchanged content can still be queried. When a mapping changes alone, no-op compilation of a valid PDF can still succeed, and the query continues to wait for the new PDF and mapping to be generated; failed compilations and no-op compilations will not accept the replaced mapping.

## Progress, cancel and compile after saving

When the client declares `window.workDoneProgress`, the server also displays the start and completion of compilation via the standard `$/progress`, which can be aborted via the editor's cancel button. Compilation continues when the client rejects or does not respond to the progress creation request.

After `onSave` is turned on, multiple saves during compilation will be merged into one subsequent compilation, and the latest saved content will be re-read. Canceling compilation or shutting down the server will also clear the queued tasks. If there are still unsaved dependencies when starting subsequent compilation, the compilation will be skipped and the reason will be recorded.

Before latexmk and the direct TeX engine are compiled, the `.aux` subdirectory in the output directory will be pre-built for the static `\include{chapters/name}`, which contains the chapter declarations indirectly loaded by `\input`. It also recognizes `include` generated by static named calls and pure aliases, and supports local packages, nested input, and comments around paths. Directory creation only handles relative static paths within the output directory, skipping macros, parent directory paths, comments and verbatim text.

## Actual input and document dependency

Dependencies in saved files will be traversed again before compilation, including local `.sty`, `.cls` and their input files; sub-file paths will also try to be resolved relative to the main documentation. In this way, when new dependencies are added to subfiles on the disk or local packages change during compilation, they will also participate in the save check and expiration result check.

After compiling, read this updated `.fls` recorder and found that the TeX macro actually read after expansion `.tex`, `.ltx`, `.sty`, `.cls`, `.def`, `.clo` , `.fd`, `.ldf`, `.bbx`, `.cbx`, `.lbx`, `.dbx` and `.bib` files, as well as PDF, PNG, JPEG, EPS, SVG images. The sources in the project directory will be entered into the index and participate in subsequent root file identification, saved compilation, and unsaved checking; system TeX packages will not be entered into the index in batches. When the first discovered source has unsaved content or disk changes occur during compilation, this diagnostics will also be discarded, and irrelevant unsaved buffers will not be affected. The last recorded dependencies will be retained until the new recorder is replaced, so the newly removed dependencies may still need to be saved first. The default latexmk and TeX engine parameters enable recorder; custom parameters need to enable `-recorder` by yourself. Tools that do not generate `.fls` still use static dependencies.

[Picture direct call and static alias](graphics-calls.md) in the project source code discovered by recorder is also used for picture dependency and candidate path checking, and common call analysis for jump, completion, and renaming. Files that are only for code display do not provide executable macro definitions; when static input is found to be incomplete, image candidate conditions will not be added based on the uncertain macro set.

The recorder confirms that even if the read image is located outside the workspace and root documentation, it will be retained as a binary dependency and participate in change checking, file notification cancellation, diagnostic refresh and PDF / SyncTeX content history verification for subsequent compilation. Images in the shared directory and external images read after macro expansion follow the same rules; equal length replacement and modification time retention can also be recognized.

The recorder also preserves the path that TeX actually opened and its physical file bindings. After a symbolic link switches targets or is deleted, even if the original target remains unchanged and the new target is earlier than the PDF, the old PDF and SyncTeX will be rejected; compilation of the unrewritten PDF will not overwrite the original binding history. Switching known links during compilation will cancel the task or discard the diagnostics; if the read target of the newly written PDF cannot be confirmed, it needs to be recompiled. New external targets with known paths will save a snapshot of the content even if they are not entered into the source code index, participating in compile-time changes and legacy PDF/SyncTeX checks. Links that are no longer read by the new recorder will not continue to affect the new PDF. When files are moved, the current dependencies are updated simultaneously, and the old product history is retained for verification.

The BibTeX/Biber log confirmation reads of `.bib` and `.bst` also retain the original path bindings, subject to the same link switching, deletion, notification cancellation and old product checks. TeX recorder and document log update their respective dependencies separately, and the truncated document log will not replace the complete history. When you just rerun TeX and reuse the old `.bbl`, the changed document link or file content will not be regarded as the source of this document; even if the original file size and modification time are retained, you still need to actually rerun the document tool. Known paths still listed in the new log will retain change checks even if they have been deleted or switched to unindexed external files; document dependencies removed by the new complete log will not continue to invalidate new PDFs, and document bindings are maintained simultaneously with directory and file renames.

When the output directory is not explicitly specified, the default latexmk call will read the direct string `$out_dir` in the project `.latexmkrc` / `latexmkrc`, and use `build/texquill` when it is not recognized. The default latexmk parameters keep BibTeX running in the main documentation to correctly handle relative paths such as `../library.bib`. When the output directory is a hidden directory, an absolute path, or contains `..` (including directories identified from rc files), the way latexmk switches directories to run BibTeX will be retained to adapt to BibTeX's file writing restrictions; in such configurations, the parent directory literature path may require additional tool configuration.

## Missing files and path conditions

File lookups for static `\input` and `\subfile` also record the identities of missing candidates, preferred suffix candidates, and selected files. When the missing source is compensated during failed compilation, even if there is no file notification, the error result will be marked as expired and the historical compilation diagnostics will be cleared; the file creation notification will cancel the corresponding task and queue. When an existing source is obscured by a higher-priority suffix file, or when a symlink is switched to another source, this also expires the results and prevents compilations that do not rewrite PDF from accepting the old product. This search tracking is not affected by `\includeonly`; the source code content still uses the original save, content changes and recorder checks.

`IfFileExists` and `InputIfFileExists` will record static local paths separately, including candidates that do not yet exist and suffix candidates with higher priority. When files appear, disappear, or symbolic links change targets during compilation, even if no file events are received, the results will be marked as expired and diagnostics will be discarded; related creation, deletion, directory change, and rename notifications will also cancel running and queued compilations, and clear old published diagnostics. Data files that only check for existence do not require saving buffers, and modifying their contents will not change the conditions; no new source code dependencies or imported symbols will be added. Sources actually identified by the recorder still obey the original dependency rules. When the missing path is located under an existing directory symbolic link, the canonical path corresponding to the latest existing parent directory will also be recorded; when a file or directory creation notification is received through the physical path, the relevant compilation will also be canceled and the old diagnostics will be cleared.

After changes in historical conditions or recorded input content, compilation without rewriting PDF will report that the product is out of date, and SyncTeX will also require recompilation; source code, pictures, documents and styles will be identified by content even if they retain their original size and modification time. When recorder information exists, the content history is based on the actual input confirmed, additional sources from the documentation tool are retained, and statically excluded chapters are not included. When the first compilation generates a PDF but the result expires, the content and conditional protection of the original input are also retained; consecutive failed no-operation compilations will not overwrite the basis of the old PDF. For opened dynamic input that is confirmed only after compilation, the disk content and editor version before compilation are retained at the same time; unsaved buffer content will not be recorded as PDF compiled content, and the timestamp saved during compilation can also be recognized. It is known that the `.aux` file corresponding to the job product and the static `\include` does not participate in the existence change check to avoid normal generation of output and invalidation of compilation. Each project can record up to 4096 candidate paths, and the input and condition history of diagnostics and PDF can retain up to 128 projects respectively, which will be re-accumulated after restarting the server; macro expansion and checks in the system TeX search directory are not within the scope of this static tracking.

The static `bibliography` / `nobibliography` database lists and `bibliographystyle` styles also record the existence status of local candidates and symbolic link targets. When a file is added, disappears, or switches targets during compilation, even if there are no file events, the results will be marked as expired and old diagnostics discarded; creation, deletion, and directory change notifications can cancel the related compilation and clear historical diagnostics. Paths are matched according to the real `.bib` / `.bst` suffix, database blank removal and style sheet rules; dynamic or incomplete lists, commands redefined within the project are not inferred. Candidates share the 4096-item limit with other file criteria; a consistently missing and unchanged database will not independently expire the compilation of prebuild `.bbl`.

The static local libraries of `addbibresource` and `addglobalbib` participate in the save check before the first compilation, and unsaved databases will prevent compilation. The path uses the full file name, not borrowed from `refs.bib` for `refs`; missing candidates are also logged. When compiling, deleting, or switching resource targets during compilation, the result will be marked as `stale` and `analysis: null` returned, even if no file notification is received. Supported options, indirect calls and static boundaries can be found in [biblatex Documentation Resources](biblatex-resources.md).

Local packages and document classes also participate in the same condition tracking, covering `usepackage`, `RequirePackage`, `RequirePackageWithOptions`, `documentclass`, `LoadClass` and `LoadClassWithOptions`. The package removes TeX whitespace according to the complete static list, retains internal spaces and commas in the class name according to the single file parameter, and reuses comments and optional parameter rules. The load command always appends the `.sty` / `.cls` suffix, and the suffix will be appended again if written explicitly; tracking uses the actual candidate file according to this rule. Packages and document classes loaded with static named calls and pure aliases also track missing candidates; when files appear, change targets, or disappear during compilation, stale results and diagnostics are discarded, even if there are no file watch notifications. Dynamic, incomplete or redefined loading commands of the same type within the project will not be statically inferred; `PassOptionsToPackage` / `PassOptionsToClass` that only pass options will not generate loading conditions, and the candidates still share the above upper limit.

Static `includegraphics` conservatively records the selected image and the existence status and symbolic link target of the previous candidate according to the image extension of the usage location, the compilation root directory and the search rules for effective `graphicspath`. Image directories that do not yet exist are also included in the tracking, and the directory alias retains the original path; image replenishment during compilation will discard the old missing image diagnostics, and image or directory creation notifications can cancel compilation, including notifications of physical paths outside the workspace. Explicit extensions and dotted name suffix fallbacks share image navigation rules, do not use sub-file directories as compilation working directories, and do not track known compilation products. Candidates share an upper limit of 4096 items; when the search directory reaches 256 items, the setting is dynamic or incomplete, the calling scope cannot be confirmed, the project is redefined `includegraphics` / `graphicspath` / `DeclareGraphicsExtensions`, or `DeclareGraphicsRule` is customized, this static image condition is skipped, and the entered recorder and content check continue to take effect.

## File notification and parsing boundaries

File monitoring notification `workspace/didChangeWatchedFiles` uses the same project refresh process as file operation notifications, which can clear cross-file compilation diagnostics in the affected project and update push or pull diagnostics. When the client supports dynamic monitoring, the server monitors source and image content changes, as well as the creation and deletion of any file name; image suffixes are not case-sensitive. Current and queued tasks are canceled when known sources or images actually change during compilation; duplicate listen notifications delivered late will not cancel tasks that are compiling the same saved content, nor will historical diagnostics that are still consistent with the compiled input be cleared; result IDs are preserved when the content and version of a pulled diagnostic have not changed. Each project saves the input snapshot corresponding to the published diagnostics. After the shared file is updated, only projects using old content will be cleared; the newly compiled input snapshot will not overwrite the basis of the old diagnostics. Both source code and binary input are checked by content and do not rely on modification time or file size; binary content such as images uses streaming fingerprints to support replacement of retention time and size. Unnotified modifications during compilation will also cause the results to expire. Data content updates that only check for existence will not cancel compilation, nor will they enter the symbol index through listening notifications.

Static condition tracking of input, images, verbatim code input and existence checks will skip the macro declaration body, parameters consumed by user macros and related commands that have been redefined to avoid irrelevant file replenishment and expiration of valid results. Actual read dynamic sources are still protected via recorder and existing content checks; execution of user macros and conditional branches is not simulated.

Verbatim code input is known to only establish static data dependencies at confirmable activity calls. Code paths in macros that are not called, or commands consumed by user macros, do not reduce the TeX sources of the same name actually executed by the recorder to display data; macro definitions from these sources can still be navigated and renamed. Normal direct display calls maintain data isolation, and related package settings, redefinitions, and dynamic file names are treated conservatively.

The static `\include` chapter that has not yet been found when compilation starts also participates in existence tracking. When chapters are replenished during compilation, old diagnostics are discarded and the results are marked as expired even if there are no file notifications; creating notifications for a file or its directory cancels the associated compilation and queue. Missing chapter warnings that have been compiled will be cleared after the catch-up notification. Old PDF and SyncTeX mappings that have not been rewritten still require recompilation, as well as files with old modification times saved. Chapters excluded by static `\includeonly` do not participate in this missing tracking; the selected name can contain `.tex`, or it can come from a loaded settings file. When the chapter selection contains macro expansion or multiple statements cannot be confirmed unanimously, missing chapter tracking will be skipped and the execution order will not be inferred; content checks and recorder rules from existing sources will continue to take effect. Candidate paths and conditional files share the aforementioned tracking and cache limits.

File condition checking and missing chapter spelling repair for chapter selection also support static naming calls and pure alias `includeonly`, which share the same set of project selection rules. Only the selected missing chapters participate in presence condition tracking, and the candidate repairs must still be in the selection list; filling in the excluded chapters will not discard valid diagnoses. The declaration body of a known pure alias will not be mistaken for a selection call; this inference is skipped when the name is dynamic, redefined, the meaning of the call cannot be determined, or the source exceeds the limit.

For directory list overrides, local and global scopes, statically declared aliases, and renaming rules, see [Image Parsing and Moving](graphics.md).
