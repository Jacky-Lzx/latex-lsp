# Explicit bibliography processing

[Back to documentation](README.md) · [Compilation configuration](build-configuration.md) · [Document compilation diagnostics](bibliography-diagnostics.md)

By default, latexmk schedules documentation tools by itself. When running pdfLaTeX, XeLaTeX or LuaLaTeX directly, `build.bibliographyTool` can be configured so that a background compilation task is responsible for generating auxiliary input, executing documentation tools, and subsequent TeX passes.

Common BibTeX projects:

```json
{
  "build": {
    "executable": "pdflatex",
    "bibliographyTool": { "backend": "bibtex" }
  }
}
```

biblatex/Biber project:

```json
{
  "build": {
    "executable": "xelatex",
    "bibliographyTool": { "backend": "biber" }
  }
}
```

`bibliographyTool` defaults to `null`, no additional stages are added. An explicit backend can be selected per root document, which can be used with `indexTools`. Only projects that actually generate literature auxiliary input should be turned on; if `.aux` / `.bcf` is missing, an error will be reported and the backend will not be automatically guessed from the log.

| Fields | Default values and meanings |
| --- | --- |
| `backend` | `bibtex`, also optional `biber` |
| `executable` | `null`, using the backend name; you can also specify an executable or wrapper |
| `arguments` | `[]`, literal parameters added before the input/output parameters managed by the server, up to 128 items |
| `dependencies` | `[]`, additional style, configuration or data files, relative to the main documentation or absolute path, up to 128 items |
| `timeoutSeconds` | 60 seconds for each backend call, configurable 1–3600 seconds |

The parameters do not pass through the shell, nor do templates such as `%f` expand. BibTeX appends the private auxiliary file name last; Biber appends the controlled `--input-directory`, `--output-directory` and private task names last. `arguments` can be used when the data model or backend options need to be adjusted; tools with different calling methods should be adapted through the wrapper, and the wrapper must still generate the corresponding `.bbl` and `.blg`.

## Output, search paths and diagnostics

The documentation tool generates output in a separate temporary directory under the actual product directory. BibTeX copies the primary `.aux` and the auxiliary file tree connected through `\@input`, and rewrites the auxiliary file paths in the staging copy; the original `.aux` remains intact. Biber uses a copy of the master `.bcf`. The staging task uses ordinary file names and is compatible with BibTeX's `openout_any=p` policy; TeX's file access settings are not modified.

The working directory of BibTeX is the temporary directory; the working directory of Biber is the main documentation. The server prepends the main documentation and the actual product directory in `BIBINPUTS` / `BSTINPUTS`, retains the original search terms and default search paths, and binds the original relative directory to the main documentation. Databases and local styles continue to be read from the project. The database generated by TeX in the product directory can also be found. The search path is also used to handle the source location of the log.

When `.bib` is generated in the actual product directory using methods such as `filecontents`, only the `OUTPUT` record of this complete recorder, the actual database read of the explicit backend, and the stable content/path snapshot are jointly confirmed before it is accepted as input for this generation; normal analysis results can be retained for both the first compilation and subsequent updates. This exception is limited to ordinary database files in the product directory, does not accept symbolic links, dynamic sources that lack write records, or open database buffers, and does not change the verification of other sources and file conditions.

During the execution of the explicit pipeline, the file monitoring notification of `.bib` in the product directory is handed over to the final content and backend snapshot check to avoid the compiler's own write cancellation task. External changes with no evidence of build still expire the results; overwriting the confirmed build database during backend execution causes the stage to fail and retain the old `.bbl`. Other sources, directories, and explicit file operation notifications continue to use existing cancellation rules.

After exiting successfully, generating a new ordinary `.bbl` / `.blg`, auxiliary input and explicit dependencies unchanged, and no error diagnostics in the processing log, the official `.bbl` can be atomically replaced. The original `.bbl` of this stage is retained when the backend fails, cancels, times out, is missing output, or monitored input changes. Do not treat symbolic links, directories, or FIFOs as new output; reject processing if `.bbl` is a symbolic link.

The valid `.blg` generated this time will be saved in the actual product directory, including the processing log when the tool fails. The log reuses existing BibTeX/Biber diagnostic parsing, database location and dependency logging; handling errors in the log will fail the stage even if accompanied by exit code 0 and retain the old `.bbl`. Failure results do not return a successful PDF.

## Subsequent compilation and life cycle

Each round first executes the literature backend, then executes the configured indexing task, and finally forces two TeX runs to allow the literature entries and auxiliary citations to enter the final PDF. If the auxiliary input or index input related to the document still changes, run the next round; up to four rounds, if it is still unstable, an error will be reported. BibTeX only compares the `\citation`, `\bibdata`, `\bibstyle`, `\@input` instructions and auxiliary file bindings at the beginning of the line. Changes in labels, `\bibcite` records and comments will not trigger the backend repeatedly; Biber is relatively complete `.bcf`; The database and style confirmed by the tool log also participate in subsequent convergence checks, so TeX will reprocess it when rewriting and generating the database in subsequent passes. The complete auxiliary input is still checked for changes during tool execution. The indexing process without the document stage configured still only runs TeX once after the tool.

The final diagnostics uses the last pass of TeX logs and the `.blg` actually updated in this process; the first pass of temporary literature rerun prompts will not overwrite the final results. The analysis of `latex/buildFinished` and `latex.buildStatus` includes:

```json
{
  "processedBibliographyTool": {
    "backend": "bibtex",
    "executable": "bibtex",
    "inputUri": "file:///project/build/texquill/main.aux",
    "outputUri": "file:///project/build/texquill/main.bbl",
    "transcriptUri": "file:///project/build/texquill/main.blg"
  },
  "bibliographyProcessingRounds": 1
}
```

This stage shares task ID, cancellation, timeout, progress, save check and expired result verification with `latex.build`, `latex.rebuild`, compilation after saving. Unsaved edits from known sources will prevent startup, and changing the source during execution will cause the results to expire; explicit additional dependencies have also been added to save checks and file event listening. Root documents that share the same PDF product cannot be compiled concurrently.

When biblatex explicitly requires a documentation backend, `Rebuild …` is only provided if the currently configured backend matches, and the warning only requests the current root's jobName. Multitasking requests or other names continue to remain tool summary. Check the current configuration and diagnostics again when the menu is executed; by default latexmk's existing recompilation behavior maintains its complete scheduling process.

Custom compilation of `arguments` must also configure `rebuildArguments`. Configuration and explicit dependencies are verified before the first invocation of the compiler. Maximum 8 MiB per auxiliary input, maximum 1024 copies, 64 levels of auxiliary file tree, 16 MiB total; maximum 16 MiB for `.bcf` / `.bbl`, maximum 8 MiB processing log. If the limit is exceeded, an error will be reported, and the incomplete input will not be used to continue generating documents.

## verify

```sh
cargo test --locked --test bibliography_workflow
cargo test --locked --test protocol bibliography_workflow
cargo test --locked --lib generated_bibliography
cargo test --locked --test protocol generated_bibliography
cargo test --locked --test protocol generated_bibliography_with_real_tex_and_bibtex -- --ignored
cargo test --locked --test rebuild_actions
cargo test --locked --test bibliography_workflow real_bibtex -- --ignored
cargo test --locked --test bibliography_workflow real_biber -- --ignored
```

Real BibTeX regression requires pdfLaTeX, BibTeX and plain.bst, covering subsections, hidden output directories, jobName with spaces, database updates and final PDF. Real Biber regression additionally requires Biber and biblatex; skipped by default if not installed. The default test verifies two types of calling methods, final pass, failure log, old `.bbl` retention, auxiliary input changes, dependencies and symbolic links, cancellation/timeout, non-trivial products, four-round cap, and shared document and index pipelines.
