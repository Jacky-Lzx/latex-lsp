## Support range and parameter signature

Label renaming will verify the parameter context of the declaration itself. When the label declaration of `label` or `hyperdef` is discarded, displayed, or interpreted in an unauthenticated manner as a user macro argument, the key will be refused to be renamed to prevent the displayed source text from being rewritten; the declaration command is also protected when it is replaced. The same rules are used for cross-file, static naming calls and pure forwarding, and the unsaved number of parameters or text modifications take effect immediately. The only single-argument macro whose text is only `#1` also retains label editing in the actual parameters, including TeX definitions that separate parameters with ordinary characters; outer data context, repeated definitions, and control sequence delimiters continue to be protected. Other tags remain independent; deferred declarations in the body of user macro definitions and declarations in native text parameters retain existing editing capabilities.

Navigation, completion, suspension, referencing and diagnostics of tags exclude statements that are definitely not executed: unreplaced `typeout`/`message` text, as well as parameters that were indeed discarded by the only previous normal macro definition in the same file, supporting static naming and pure forward calls, normal optional parameters and TeX delimited parameters. Data declarations do not satisfy undefined references, do not produce local or cross-file duplicate warnings, and are not the source targets of compilation warnings. Cross-file unsaved replacements for native message commands are updated immediately; shared files retain claims while they may still be executed in either consumer project. Unknown execution, conditional/local definition, subsequent definition, macro modification interface, dynamic naming/loading and analysis of over-limit retained structure index; `providecommand`/`providerobustcmd` may retain existing commands and discard the authentication parameters accordingly. Rename integrity protection continues to be independently verified. If the complete text of the only ordinary single-argument macro is exactly `detokenize{#1}`, `typeout{#1}`, or `message{#1}` without replacement, the label in the parameter will also be treated as data; lexical blanks, comments, and pure forwarding/static naming calls are allowed. Mixed executions, unknown outer packaging and packaging formats are not certified hereunder. Readers in the declaration body and default values may be removed by the caller and the remaining tokens executed, retaining the structural identity of the tags. The load order, format conversion wrappers, copy readers, and full deferred execution identities of cross-file drop parameters are still to be authenticated separately.

PDF target renaming also verifies parameter identity in the complete shared consumption project. When the `hypertarget`, `hyperdef`, `pdfbookmark` statement or `hyperlink`, `hyperref` reference appears in a message, discard, display or unauthenticated parameter, or when the corresponding original command is replaced, the target is refused to be renamed; for example, `\typeout{\unexpanded{\hypertarget{ghost}{Text}}}` Only text is output, `ghost` in the log cannot be overwritten. Pure forwarding, copying, static `csuse`/`csname` may use the target with the same name but does not enter the editable index. Partial editing will also be rejected to avoid damaging the link by only changing the statement. Direct calls, native text packaging, authenticated single-parameter transparent transmission, deferred declarations in the definition body, and irrelevant targets retain existing edits; the macro name can still be changed independently. Unsaved provided files and new shared roots are immediately involved in the check; target renames are rejected when the source code or alias analysis exceeds the limit. No macro expansion is performed, and possible indirect calls are not certified as navigable targets.

If all candidates for repeated definitions have the same parameter syntax, parameter analysis only restores the common read boundary, and retains the source code such as independent references and file calls after the actual parameters have been completed. For example, after two single parameters `one` are defined, `\one{Text}\ref{same}` will no longer swallow `ref`. The number of parameters, separators, asterisks/flags, whitespace rules, and square bracket reading must be consistent; documentation and optional parameter defaults do not affect boundaries. Pure forwarding and static named calls follow common boundaries, and unauthenticated copies, unknown claims, or external unconfirmed definitions continue to be protected. This analysis does not authenticate the execution of the macro text, does not restore unique signatures, and does not treat labels or references in actual parameters as executed source code; unfinished parameters continue to be protected by data.

The arguments of `typeout` and `message` are expanded to the message text, and non-expanded tokens therein are not considered executed claims, citations, or bibliographic queries. Tag keys do not provide destructive renaming, nor do undefined diagnostics arise from references in them; the initialized biblatex text wrapper also does not make `entrydata` in the message a real query. Direct, statically named, pure forwarding, and confirmable copy calls use the same parameter boundaries, and unfinished message text continues to be protected. The common macro names involved in expansion in the text can still be renamed, and the message commands can be replaced in the project and reanalyzed.

This is a runnable basic version that uses static parsing and does not perform TeX macro expansion; for help with distribution file search and selected commands, see [TeX distributions and packages](distribution.md). Custom commands support declarations such as `\newcommand`, `\renewcommand`, `\providecommand`, `\DeclareMathOperator`, `\DeclareRobustCommand` and xparse’s `\NewDocumentCommand`, including curly braces and direct control sequence forms; also recognize `\def` / `\gdef` / `\edef` / `\xdef` and `\let`. BibTeX supports common `{...}` / `(...)` entries and nested fields.

User macro signature help identify the number of parameters/first optional parameter default value for `\newcommand` series and `\DeclareRobustCommand`, xparse’s `m` / `o` / `O{...}` / `s` / `t+` / `d<>` / `D<>{default}` / `r()` / `R(){default}`, and `\def` series of consecutive `#1#2...` parameters. Optional parameters and default values for legacy macros and environments end at the first unprotected brace `]`, leaving the literal `[`; xparse calls still match nested square brackets. Direct calls, `csuse` and static `csname` use the rules of the called command, supporting asterisks, nested calls, escaping and multi-line comments. The `t` flag supports characters, control sequences and Unicode tokens, and retains the subsequent parameter number when there is no flag; the delimited parameter supports characters, control sequences and Unicode delimiters, matching nesting, brace protection and complete tokens; conservative fallback when required delimiters are missing. Signatures will not be inferred temporarily when unsupported parameter specifications, string evaluations, or definitions are ambiguous; no prompts will be made in comments and verbatim text.

If the group text of a zero-argument macro contains only one control word, argument hints and command completion will also inherit the target signature along the static alias chain within the current project, showing the alias being called and where it was declared. Supports traditional declarations, TeX definitions, named definitions and xparse empty parameter specifications, allowing text peripheral comments and whitespace; completion only inserts required parameters, retaining existing optional parameters, flags and delimited parameters. Loops, unknown targets, redefinitions, expansion definitions, and other texts do not infer forwarding signatures; empty macros and parameterless switches do not generate argument snippets.

Required parameters also support single ASCII characters without curly braces, control words, control spaces, and escape symbols, such as `\pair a{body}`, `\pair\payload{body}`, and `\frac12`. Direct calls, `csuse`, static `csname` and environments use the same token boundaries and retain the lexical whitespace rules for subsequent `!` parameters. Ungrouped Unicode, `^^` character escapes, and explicit `\par` are not currently inferred as a single argument; Unicode within curly braces is supported normally to avoid confusing pdfTeX's UTF-8 bytes with XeTeX's character tokenization. The label endpoints of the reference range still require curly brace grouping, consistent with the identification rules for navigation and renaming.

The optional parameters at the end of ordinary xparse commands and environments support the `!` modifier: valid spaces will end parameter reading, lexical blanks immediately after comments and control words are processed according to TeX rules, and blank lines retain paragraph boundaries; `csuse`, direct environment calls and `begin` each maintain the actual reading method. Invalid `!` This modifier in positional and expandable declarations does not infer the signature. For example, under the specification `m !o`, `\probe{body}[note]` will read optional parameters, while the square brackets of `\probe{body} [note]` belong to the text.

When a client that supports snippet completes user macros, it will also generate a tabstop of required parameters based on the same signature. For example, `\newcommand{\pair}[2][blue]{...}` will be complemented by `\pair{...}`, retaining the default value of the first optional parameter; the xparse asterisk, `t` flag, and optional delimiter parameters are also omitted by default. The required delimiter parameters retain the delimiter, and correctly escape snippet special characters and separated control words. When there are grouping, flag, and delimited parameters after the macro, or ASCII arguments without curly braces on the same logical line, only the command name will be replaced, and the comment continuation line will be retained; the text after ordinary line breaks will not suppress parameter placeholders. Continue to provide command name completion when the client does not support snippet or when the signature cannot be safely inferred.

Environment signature help supports `\newenvironment`, `\NewEnviron`, xparse's `\NewDocumentEnvironment` family, and common environments such as `tabular`, `minipage`, and `figure`. Theorems declared with `\newtheorem` show an optional `[note]` title. Arguments are available through `\begin{panel}` and direct `\panel` calls; command completion for custom environments inserts required-argument placeholders and preserves optional defaults. Custom commands and environments recognize conventional argument counts/defaults and xparse's `m`, `o`, `O`, `s`, `t`, and `d/D/r/R` specifications. Unsupported specifications and multiply defined names do not produce inferred signatures. etoolbox's `newrobustcmd`, `renewrobustcmd`, and `providerobustcmd` also support navigation, symbols, completion, signature help, and cross-file rename, including starred declarations, declarations without braces, and literal `csname` declarations expanded through `expandafter`. Completion preserves the first optional argument's default.

The LaTeX core's `NewExpandableDocumentCommand`, `RenewExpandableDocumentCommand`, `ProvideExpandableDocumentCommand` and `DeclareExpandableDocumentCommand` share macro navigation, citation, renaming and completion with normal document commands, and are compatible with braced or bare command targets and the static `csname` form. The statement provides signature help for commands, parameter specifications, and definition bodies; the call supports `m`, `o`, `O`, `s`, `t`, and `d/D/r/R` separated parameter specifications and modifiers, and completion retains optional parameter default values. Complex specifications will continue to be conservatively rolled back and macro expansion will not be performed.

`NewCommandCopy`, `RenewCommandCopy` and `DeclareCommandCopy` support navigation, referencing, completion and renaming of copy targets, and provide declaration signature help and snippets. The copy target is an independent macro; when renaming the original command, the source parameters of the copy declaration are maintained, and when renaming the copy, only the declaration and call of the copy are updated. Compatible with braced or bare command parameters, as well as the static `csname` notation of the target, preserving comments and verbatim content.

Direct control word targets of `futurelet` and static `csname` targets of explicit `expandafter` expansion are also entered into the symbol index, supporting cross-file navigation and safe renaming. Subsequent tokens will still be processed as continued execution; see [Forward Target](futurelet.md) for examples and support boundaries.

Control words in the declaration target and copy source are retained as command name references, and subsequent ordinary text is not registered as statements or parameters of the command; for example, copying `newcommand` will not create duplicate definitions. For the editing boundaries of labels, environment and other names, see [Command Name Operands](declaration-operands.md).

`meaning` When viewing commands, macro name navigation and rename references are also retained, and the viewed commands are not used as calls. For the subsequent processing of ordinary grouping and primitive rewriting, see [meaning operand](meaning.md).

The compile special character diagnostics also reserves [Parameter candidate for copy command](literal-macro-scopes.md#command-and-environment-copy) to avoid mistakenly repairing the parameters consumed by the copy as text characters; this check does not infer the definite signature of the copy call.

`NewEnvironmentCopy`, `RenewEnvironmentCopy` and `DeclareEnvironmentCopy` support environment navigation, referencing, renaming, semantic highlighting and declaration signature help. The second parameter is processed according to the source environment and supports the completion of complete, incomplete and cross-line names; this parameter is updated synchronously when the source is renamed. The copy's `begin` / `end`, directly generated commands, and static `csname` calls use the copy's own name; the original counter continues to be used when copying the theorem, and it is not inferred that the copy has a counter with the same name. Source names that contain semantic gaps or are dynamic are not statically matched.

`DeclareTextCommand` / `ProvideTextCommand` and its `Default` form support navigation, referencing, renaming, declaration signature help and call parameter inference of text macros. Encoding parameters are independent of macro arguments; completion omits optional parameters to retain default values. The zero-argument symbol of `DeclareTextSymbol` enters the index in the same way as the single-argument accented command of `DeclareTextAccent`, and is compatible with bare commands or curly brace targets, retaining encoding, character slots, and definition bodies.

## Environment and static call analysis

- Macro argument analysis also recognizes static ASCII prefixes and delimited parameters in TeX definitions, compatible with `def`, `gdef`, `edef`, `xdef` and corresponding etoolbox named definitions. Delimited control words are matched according to complete tokens, and delimiters of the same name protected by curly braces are skipped. Normal spaces, tabs, newlines, comment continuation lines, multi-token delimiters and static aliases are supported. Continuous typesetting whitespace is normalized according to TeX space tokens. Lexical whitespace after control words is ignored. Comment continuation lines do not generate spaces. Normal commands after the call are completed continue to participate in diagnostics and editing. This rule is only used to identify commands consumed by macros, and does not add signature help or completion fragments for such macros; it does not infer parameter text containing empty paragraphs, non-ASCII, `^^` writing, or more than 64 delimited tokens.

- Static `\csuse{name}` and literal `\csname name\endcsname` calls also use macro signatures within the current project to identify arguments, covering grouping, optional arguments, xparse flags, TeX-delimited arguments and static aliases. Semantic spaces after the name group are retained, and lexical spaces after `endcsname` are ignored; naming declarations are not treated as calls, and the call target is not inferred when the related naming command is redefined. Normal file repair and color renaming after the call is completed still works; no dynamic names or arbitrary macro expansion are performed.

- The start command of the custom environment also participates in macro argument analysis, supporting traditional and xparse-declared required, optional and delimited parameters, as well as direct calls, static named calls and aliases. `begin{environment name}` is read according to the actual boundaries of the environment parameters, and also recognizes static `\csuse{begin}`, literal `\csname begin\endcsname` and environment names after pure alias calls; environment parameters are not inferred when `begin` is redefined or the target is uncertain. The text after the parameters have been completed continues to participate in file repair and color renaming; the purely static aliases of the environment start and end commands also inherit the parameter rules of the target, and the normal commands after the end call continue to participate in analysis; the environment name, the generated end command and the ordinary macro name remain ambiguous when they conflict. Environment declarations in the paused parent file also participate in conflict checking and are revalidated before applying old fixes. The environmental declaration itself provides signature help for names, parameter specifications, and start and end codes. Declared parameter specifications and default values are also processed as data, and normal color references in the start and end code can still be renamed. This rule does not perform environment context or dynamic macro expansion.

- The environment name also supports ungrouped ASCII single-character parameters (such as `\begin x`), which is compatible with static naming calls and aliases; the environment parameters continue to be analyzed according to the parameter rules of the environment. Environment pairing diagnostics, jumps, references, and renames recognize this name and auto-complement curly braces on renames to support multi-character new names; ungrouped non-ASCII characters, control sequences, or `^^` notation are not inferred.

- Environment references, jumps, and renames also recognize static `\csuse{begin/end}`, literal `\csname begin/end\endcsname`, and environment name groups after purely static aliases, preserving comments and versioned edits. Aliases are resolved according to the project scope of each main document; the same location in a shared file has inconsistent meanings in different projects, or when indirect environment calls are used as macro arguments, renaming is refused to avoid omissions or mistaken changes. Dynamic names and arbitrary macro bodies do not perform expansion.

- Environment pairing diagnostics and repair also parses statically named calls and aliases by project, and ordinary and indirect start and end calls can be mixed; deletion and repair of unexpected end calls cover the complete command, and missing end calls are filled in before the end of the outer environment. The shared file only provides consistent pairing repairs for each project. The definition text of macro data and uncertain execution retains uncertainty by name. The dynamic environment parameters in the text are not regarded as actual environment names; real pairing errors, verbatim environment errors and compilation diagnostics of other names are still retained. Re-parse aliases in dependencies before applying the old fix to avoid deleting legitimate calls after alias changes. Pairing is performed across files in the order in which static `\input` and `\include` appear in the main document, and nested input is supported; the fix for missing end calls across files points to the actual closing position and is associated with the starting file. Repeated inputs and edits to shared files must be consistent across executions and root documents; loops, conditionals, dynamic input, or semantically uncertain `\endinput` do not use incomplete sequences to generate pair fixes. No arbitrary macro expansion is performed.

The custom environment supports declarations such as `\newenvironment` / `\renewenvironment`, xparse's `\NewDocumentEnvironment`, `\NewEnviron` / `\RenewEnviron` and `\newtheorem`, providing completion, definition jump, reference, suspension, symbol and cross-file renaming. When renaming, `\begin{panel}` / `\end{panel}`, directly called `\panel` / `\endpanel` and literal `\csname panel\endcsname` are maintained simultaneously; you can jump from these calls or initiate renaming. Check the environment-generated macros with the same name and the `\end...` macro to avoid conflicts with existing commands; when there is a direct control sequence call, the new name must only contain TeX command letters.

Whitespace inside environment and counter names has semantics, for example `panel` and ` panel ` can be declared separately. Navigation, referencing and renaming do not merge them, and renaming of ordinary names retains other names containing spaces. Names containing whitespace are not currently entered into the static symbol index, and precise compilation diagnostics or spelling repair is not provided; typesetting whitespace outside parameters is not affected. Verbatim environments are only recognized by their actual names and do not treat ` verbatim ` as `verbatim`.

## Fonts and math commands

The fontspec's `newfontfamily` / `renewfontfamily` / `providefontfamily` / `setfontfamily` and corresponding `fontface` declarations also support command completion, navigation, hover, referencing, and safe renaming across files. Identifies bare commands and command targets wrapped in curly braces; the declaration provides fragment and signature help, distinguishes optional features before and after the font name, and the generated font switching command is treated as zero parameters. Inherit project isolation, conflict and ambiguity checking, retain font names, attributes, comments and verbatim text, and do not expand dynamic declarations.

The LaTeX standard `DeclareTextFontCommand`, `DeclareMathAlphabet`, and `DeclareSymbolFontAlphabet` also enter the command index, and the generated commands provide prompts and completions based on individual text parameters. `DeclareFixedFont` and command-targeted `DeclareMathSymbol` go into variable indexes as zero-argument font selectors or symbolic constants; character targets are not mistakenly marked as command declarations. Each of the five declarations provides command snippets, field signature help, and safe renaming across files, preserving encodings, font families, glyphs, font sizes, math categories, and character slots.

`DeclareMathAccent`, `DeclareMathRadical`, and the command-targeted `DeclareMathDelimiter` are also indexed, supporting navigation, referencing, semantic highlighting, and safe renaming across files, and providing declaration fragment and field signature help. The accent and radical commands provide invocation prompts with a required argument; the radical does not infer the number of options. The delimiter is a zero-argument notation that can be used directly or followed by `left` / `right` scaling; character targets are not mistakenly marked as command declarations. Renaming preserves math categories, font sizes, and slots, and leaves comments and verbatim text unchanged.

Commonly used standard mathematical accents and delimiters (such as `hat`, `widehat`, `vec`, `langle`, and `Vert`) provide candidates for completion, hover explanation, and command spelling repair. Accents, underlines, and `sqrtsign` press an expression signature help and completion, and delimiters do not append parameters; command and environment renaming will also check these built-in names to avoid overwriting existing math commands.

Standard Greek letters and their variants, upper and lower case forms, and common operators (such as `epsilon`, `varepsilon`, `Gamma`, `sin`, `log`) also provide completion, hover description, spelling candidates, and rename conflict protection. Letters and operators do not add call parameters; amsmath's `operatorname` / `operatorname*` and `DeclareMathOperator` / `DeclareMathOperator*` provide field prompts such as text and command targets, and are compatible with bare command targets, comments and cross-asterisks.

mathtools' `DeclarePairedDelimiter` / `DeclarePairedDelimiterX` / `DeclarePairedDelimiterXPP` declarations also support navigation, referencing, hovering, symbols and cross-file renaming. Signature help recognize asterisk automatic scaling and `[size]` manual size. The number of literal parameters of X/XPP is limited to 1–9; completion only inserts the required parameters in the text and retains their actual parameter numbers. The declaration itself provides command snippets and signature help. The number of square bracket parameters in X/XPP is required; when the dynamic number or definition is ambiguous, the call signature is not inferred. The delimiters of existing call parameters and declarations, and the surrounding code remain unchanged.

Names used only by the literal `csname` support hyphens and Chinese; when there is a direct control sequence, the new name must be able to form a TeX command, and no completion is provided that cannot be typed directly. New names conflict with macros, registers, environments, other switches, or built-in conditional primitives, and shared files that point to independent switches in other projects refuse to be modified; dynamic declarations are not expanded.

etoolbox's [String Test](string-tests.md) indexes data parameters and conditional branches separately; renames token strings retained for comparison, and updates references in declarations and branches.

etoolbox's `newtoggle` / `providetoggle` uses an independent namespace, supporting `settoggle`, `toggletrue` / `togglefalse`, `iftoggle` / `nottoggle` and the above expressions `togl {name}` operand. Provides name and value completion, fragments, signature help, boolean symbols, cross-file navigation and safe renaming; booleans with the same name remain independent. ## Naming macros, copying and aliasing

Ordinary custom macros also support the definition jump, suspension, reference, highlighting and renaming of the literal `\csname hello\endcsname`, and are processed in the same manner as the directly called `\hello`; the lexical separation blank and calling parameters after the `csname` control word are retained. Identify `\expandafter\def\csname hello\endcsname#1{...}`, `gdef` / `edef` / `xdef`, `newcommand` / xparse series and `let` alias definitions with the same spelling; renaming can be initiated from the literal definition, and the signature help are consistent with the direct definition. Literal calls can prompt built-in commands, custom macros and environment parameters, and the signature retains the `\csname ...\endcsname` writing method. Macro expansion, comment splicing, semantic gaps and unclosed `csname` in the name are not inferred and will not be mistakenly remembered as redefining the `csname` primitive; renaming is rejected when shared calls point to different macros in different projects.

etoolbox's static `csdef` / `csgdef` / `csedef` / `csxdef` declarations enter the macro index, support navigation, symbols, signature help, completion and cross-file renaming, and maintain direct calls, `csuse` and literal `csname` references. Recognizes consecutive `#1#2...` parameters and Chinese or hyphenated names called by name only; does not expand dynamic names, does not infer complex delimited parameters, does not simulate local scopes or override orders for duplicate definitions.

Macros declared and called with only static names can be renamed to Chinese, hyphenated, or numeric names, such as `release-mode`; the same applies to literal `csname` declarations expanded by `expandafter`. When there is a direct declaration or direct call in any project using this definition, the new name must still contain only ASCII letters or `@` to avoid breaking TeX control sequences. Renaming preserves ordinary strings, comments, and verbatim text, and checks built-in primitives for conflicts with existing definitions.

The renaming of macros and environments will protect the core primitives of TeX/e-TeX, including input and output, character categories and character codes, boxes, automatic execution of token lists and expression operations, such as `write`, `catcode`, `shipout`, `numexpr`. These names are also used for static name completion and command spelling suggestions; existing engine-specific primitive protection is preserved.

Static control sequence names in etoolbox's `csuse` / `csmeaning`, `ifcsdef` / `ifcsundef` / `ifcsvoid`, macro type detection and name comparison commands support completion, navigation, referencing and renaming; recognize `ifcsequal` / The two name parameters of `ifcsstrequal` retain the string and conditional branch text of `ifcsstring`. Derived environments, counters, and Boolean commands still belong to the original declaration. `csuse` calls can display signature help for the called command or environment, including optional parameter default values; dynamic names are not inferred.

The name parameters of these named interfaces are matched as is; leading and trailing blanks belong to the command name, and names containing blanks will not be merged into ordinary control words. When known name completion is selected, the entire name parameter is replaced, and inter-line whitespace is removed by additional editing, leaving subsequent parameters intact.

Named macro modification interface `csappto` / `cspreto` and its expanded, global variants (`cseappto`, `csgappto`, `csxappto`, `csepreto`, `csgpreto`, `csxpreto`), and `csundef` / `csgundef` Fragments, signature help, name completion, navigation and cross-file renaming are also supported. Only name parameters are associated with the original declaration, leaving plain text in appended or prepended code and independently identifying macro calls therein; modifications are not inferred as new declarations.

The static alias declaration of `cslet`, `letcs`, and `csletcs` distinguishes the target and the source: the alias has independent symbols, navigation and renaming, and the source parameters are associated with the original macro; renaming the original macro will maintain these references. Supports control sequence parameters with and without braces, name completion, fragment and declaration signature help. Pure name aliases can be changed to Chinese names; dynamic targets do not mistake the source as a declaration, do not expand dynamic names, and do not infer parameter signatures for alias calls based on the source or simulate subsequent reassignments.

`\expandafter\letcs\csname alias\endcsname{source}` recognizes both literal alias targets and expanded source names, supporting name completion, signature help, renaming across files and shared projects, and derived commands such as environments, counters, switches, etc. as sources. Only adjacent explicit `expandafter` and full static `csname` inherit this rule; dynamic targets do not infer the position of the source parameters.
