## Synchronization, completion and document browsing

- Full text formatting: supports `textDocument/formatting`, default tex-fmt, optional latexindent; use current buffer, retain LF/CRLF, and reject expired results. For configuration and tool requirements, see [Formatting](formatting.md).

- Range and formatting during input: support `textDocument/rangeFormatting`; after line wrapping and inputting `}`, you can also use the built-in `textDocument/onTypeFormatting` to adjust the indentation of the current line, support configuration off, UTF-16, CRLF and verbatim code protection, see [Formatting](formatting.md) for details.

- Document synchronization: full or incremental updates, using UTF-16 locations, supports Chinese, emoji and CRLF; reject invalid edits and expired versions.

- Language recognition: Recognize the editor's `languageId` when opening the document, supporting `latex` / `tex` / `plaintex`, `bibtex` / `bib` and `bst` / `bibtex-style`, unnamed buffers and non-standard extensions also get corresponding functions. The confirmed source code, database or style role of the project takes precedence; unknown language types continue to be identified by extension. The editor language setting is retained with incremental editing and file movement, and the disk content, project, and extension rules are restored after closing; unsaved documents still need to be saved as available root documents before they can be compiled.

- Completion: Common LaTeX commands, environments, user commands, cross-file labels, citation keys and paths, as well as BibTeX entry types, field names, and string abbreviations. See [Completion](completion.md) for the rules for fragments, replacement ranges, and command name operands.

- Floating prompt: built-in command description, label/document/custom command definition location; the only user macro also displays the continuous [Document Comment](command-documentation.md) before the statement, supporting cross-file and unsaved updates.

- Signature help: signatures of commonly used commands, environments, and cross-file user macros/environments, distinguishing required/optional parameters and tracking current parameters. For details on declarations, comments and optional parameter boundaries, see [Signature help](signatures.md).

- Definition and declaration jump: supports standards `textDocument/definition` and `textDocument/declaration`, covering `\ref` / `\eqref` / `\cref` and other references, common `\cite` variants, custom commands, input files, literature files and local packages, classes, and pictures. Static TeX analysis uses the source code definition as the declaration location, and both requests use the same project scope and unsaved content.

- Find references: tags, citation keys, custom commands; supports inclusion or exclusion of definitions.

- User macro call hierarchy: supports standard prepare/incoming/outgoing call hierarchy, summarizes static direct calls and file top-level calls of unique user macros, supports cross-file, recursive and expired node verification. For the scope and usage method, see [User Macro Calling Level](call-hierarchy.md).

- Document highlighting: distinguish definitions and references in the current file; the selection range can be expanded to words, complete reference keys, parameters, commands, chapters and the entire document. Citation keys preserve literal double quotes, brackets, and Unicode; support normal citation lists, biblatex multigroup/volume/data citations, classification assignments, and natbib aliases. Tag lists, range reference endpoints, and individual tag parameters for hyperref and refcount also retain full keys. BibTeX entry relationships extend from keys to entire field values, assignments, and entries. When the last line of a cross-line call contains text, the text line will not block the selection level of the complete command; the comment range does not include CRLF carriage returns, and all levels maintain a strict inclusion relationship.

- Selection ranges for BibTeX normal fields, `@string` and `@preamble` include literal content, quotes or braces, single string/numeric operands, complete `#` concatenation expressions, assignments and entire constructs. Preserve trailing whitespace for nested groups and unclosed literals; comments or punctuation in different literals will not be matched into cross-value groups. Choose to use only the source structure, without expanding strings or changing abbreviation citation or renaming rules.

- Semantic highlighting: Supports standard LSP semantic tokens in full text and specified ranges, distinguishes commands, registers, environments, tags/PDF targets/citation keys, URLs, verbatim text and comments, and marks static declarations. BibTeX also highlights entry types, field names, string abbreviations, literals, numbers, `=` and `#` operators, and interfield and top-level comments; the same rules apply for `@string`, `@preamble`, and unclosed literals. Citation keys in relational fields retain reference semantics, and `%` within literal values retain string semantics. The output is a non-overlapping single-line UTF-16 token, compatible with Chinese, emoji, CRLF and incremental editing.

- Semantic highlighting incremental results: `semanticTokens/full/delta` is supported, only the changed token segment is returned; if there is no change, an empty edit is returned. Snapshots are isolated by document and result ID and cleared when the document is closed; expired IDs, cache eviction, or large documents automatically fall back to full-text results. Each connection retains up to 16 snapshots, totaling 65,536 tokens, and range queries do not affect full-text snapshots.

  Range queries are compatible with end-of-file viewports and column positions beyond the end of the line used by the editor, including files without end-of-line wraps; positions in the middle of surrogates are still rejected, and document editing continues to use strict positional checking.

- Document symbols: section titles, Beamer frames and blocks, nested lists and list-item previews, columns, figures, tables, theorem/proof environments, labels, custom commands, handwritten `bibitem` citation keys, BibTeX entries, and string abbreviation declarations; returns a hierarchical or tiled list depending on client capabilities. Handwritten citation keys are organized by chapter, using the actual key name range, and also participate in workspace symbol search; unsaved incremental edits will update the results synchronously.

  Beamer titles are read from `\begin{frame}{Title}`, optional overlay/options forms, or a frame-local `\frametitle{Title}`. Frame selections point at the title; list-item selections point at `\item`, and their scope includes nested lists until the next sibling item or the list's closing marker. Item names show up to 80 Unicode characters of the first content line. Empty titles/items retain a nonblank fallback. Comments, verbatim text, quoted operands, and unused definition bodies do not create structure. These are source-local scopes, without executing macros or expanding generated slides. Structural nodes use Object kinds with environment-name details, Array for `itemize`/`enumerate`/`description`, and EnumMember with detail `item` for entries. Clients that filter to section headings must enable these kinds to display them.

- Workspace symbol search: Search across files for chapters, tags, macros, and citation keys (including static `ids` aliases), supports Chinese, case-insensitive, and subsequence matching, returning up to 256 items by relevance. The document outline lists the aliases under the corresponding field, and after selection, it directly navigates to the statement.

- Document folding: sections, nested environments, multi-line braces, continuous comments, verbatim environments and multi-line formulas; BibTeX supports complete entries and special entries. UTF-16 column positions, collapsed preview text, and quantity limits are provided based on client capabilities, and unsaved edits are updated immediately. For syntax boundaries and verification commands, see [Document Collapse](folding.md).

The percent encoding of local file URIs is unified into the same document identity, and compatible editors use lowercase-encoded Chinese paths and escaped ASCII file names; document synchronization, project indexing, compilation diagnostics, navigation, and versioned editing share the same content, and the file name case is preserved.

BibTeX [String abbreviations](bibliography.md#string-abbreviations) also supports case-insensitive navigation, citation, hover, semantic highlighting and safe renaming, preserving the same-named citation key and literal text.

## Diagnostics, quick fixes and renaming

Warnings where the compiler explicitly requests compilation again also provide a [Recompile Action](build.md#recompile-from-diagnostics), which can be called directly from the quick fix menu.

- LSP 3.17 diagnostic pull: Negotiate support for `textDocument/diagnostic` and `workspace/diagnostic`, merge live, project duplicate definitions and compile diagnostics; return result ID, omit entries if unchanged, return to disk contents after closing, clear results at old location after moving or deleting files. Support client refresh request, re-pull after compilation is completed and cross-file editing; old clients continue to receive push diagnostics. The result cache is isolated per connection and limited in size.

- Real-time diagnostics: unclosed/redundant curly braces, environment mismatches, duplicate tags or citation keys within the same file, and duplicate tags and citation keys across files in the same project.

- Quick fixes: Complete missing curly braces, closing environments, remove redundant closing symbols, and spelling suggestions for tags, citation keys, commands, environments, counters, and PDF targets in compile diagnostics; support versioned editing and imperative operations for old clients, and reject out-of-date fixes. Multiple compilation warnings at the same location can be repaired individually, and the same replacement can be merged into batch requests.

- Linked editing of environment names: supports standard `textDocument/linkedEditingRange`, synchronizes the currently matching `\begin{name}` and `\end{name}` names, distinguishes nested and duplicate environments; supports static `\csuse`, literal `\csname` and pure aliases (can be defined in other files within the project), retaining comments on both sides of the name. Supports Chinese, asterisk, UTF-16, CRLF and incremental editing; when whole word replacement temporarily generates `\begin{}…\end{}`, it still returns two zero-width input positions, and you can continue to enter new names. Empty names do not participate in symbol indexing or diagnostic pairing. Common verbatim environments only link the parser to confirm the true boundaries. Pair local packages, class files and input files in the order of execution (including static indirect loading), and only return a pair of ranges within the same document; repeated input and shared files must be consistent in all execution and consumption projects. Macro parameter data, definition text, redefined `begin/end`, dynamic names, unmatched structures, and undetermined input or conditional branches do not provide linkage; bare single character parameters need to be supplemented with parentheses, and use [Rename](symbols.md#environment-and-static-call-analysis) for processing.

- Cross-file renaming: tags, BibTeX citation keys, custom commands and environments; environments synchronize modification statements with `\begin` / `\end`, citation keys synchronize update of references between entries. Supports preparation for renaming, definition ambiguity/duplication checking and versioned workspace editing, skipping comments and verbatim text.

Repeated definitions across files will mark each key name and provide jumpable associated definitions; diagnostics for other open files will be refreshed synchronously when editing, closing buffers, disk file changes, or project dependency adjustments. Keys with the same name between independent papers do not conflict with each other, and shared definitions will summarize conflicts in actual use projects. This check requires no compilation and is analyzed as a static dependency; no attempt is made to expand macros or simulate TeX conditional branches.

Currently there is no built-in PDF preview or mathematical semantic checking; the default compilation generates SyncTeX data, which can be accessed by the preview plug-in for two-way query. Undefined tags and citations have [configurable on-the-fly static checking](static-diagnostics.md), and relevant warnings confirmed by the compiler will also be displayed and deduplicated. Definitions and references are looked up by project scope; renaming requires that the name has only one definition in the index, and the operation is rejected if there is ambiguity. Built-in commands do not support renaming.

## Color preview and named colors

- Color preview and color picker: Standard `documentColor` / `colorPresentation` supports those explicitly specified in `definecolor`, `color`, `textcolor`, `colorbox` and `pagecolor` `rgb`, `RGB`, `HTML`, `gray`, `cmyk` literal color. Editing preserves the command, name, surrounding whitespace, comments, and text; changing the grayscale color to color simultaneously changes the model to `rgb`. No named colors, blending expressions, or dynamic macros are inferred, and transparency editing is not provided.

- These color commands also provide completion snippets, hover descriptions, and signature help, and existing parameters are retained during completion. `definecolor` distinguishes optional types, names, optional prefixes, models and color values; the optional parameters of the color command end at the first `]` that is not protected by curly braces, and the text after the call is completed no longer triggers signature help.

- Named colors support jump, hover, reference lookup, highlighting, symbol lists, semantic highlighting and versioned renaming across file definitions: recognizes `definecolor`, `providecolor`, `xdefinecolor`, `colorlet` declarations, as well as static names in commonly used text, box, page, table colors and color extraction/conversion commands. Mixed colors such as `-accent!35!red!50!white` Edit only the name, retaining inverse symbols, proportions, text with the same name, macros, labels, comments and verbatim content. Color parameter completion provides built-in color and current project declarations, supporting in-word substitution and unclosed grouping; the latter three declarations also provide fragment and signature help.

- Comments around names and between color mixing operators also support navigation, renaming and completion, preserving comments, line continuation indentation, CRLF and proportion; static types, prefixes and model parameters can also be annotated. When the name itself is split by comments, it will not be automatically renamed or replaced to avoid deleting comments in a single edit.

- Color renaming supports names starting with ASCII letters, numbers, or underscores, and subsequent letters, numbers, underscores, dashes, and dots are allowed; only the indentation of TeX comments and their continuation lines is eliminated, and other name spaces are not normalized. Reject multiple definitions, conflicts with built-in colors or existing names, and cases where shared files point to different definitions in different projects. Reject renaming when encountering dynamic color arguments, command redefinitions, indirect calls, batch declarations, or unresolved hyperref/TikZ/tcolorbox color settings; this static analysis does not perform TeX macro expansion.

- When the color command is recognized as an actual parameter of other user macros, both prepare to rename and rename will be rejected to avoid modifying the ordinary text output by the macro as a color name. Parameter analysis summarizes the macro signatures in the current project, supporting cross-file parameterless macros, completed parameter calls, and common font switching, masking, color mixing, table and color output commands; macros with the same name in other projects are not included in the analysis.

- Commands in required groups, optional parameters and xparse-delimited parameters of user macros are also processed as actual parameters. Color renaming and compilation error fixes will not misjudge them as directly executed commands; when the signature is unknown, the same rules are used for confirmable groups. The built-in format commands and their purely static aliases still analyze the text normally. For example, the color reference in `textbf` can continue to be renamed; subsequent commands after the call is completed also participate in the analysis normally. This rule does not evaluate whether the user macro executes, discards, or displays its arguments.

- If the group text of a zero-argument macro contains only one control word (peripheral whitespace and comments are allowed), color analysis will inherit the target's parameter rules along the static alias chain, including optional parameters, asterisks, flags, and delimiter parameters. Supports traditional declarations, TeX definitions, and xparse empty parameter specifications; loops, unknown targets, redefinitions, and expansion definitions are conservatively rolled back, and true empty macros and parameterless font switching can still be used normally. This rule does not evaluate any macro text.

- `definecolor`'s color preview and color picking editing also support empty type, `[named]` and static optional prefixes, and editing retains these parameters. `[ps]` type and custom type may change the actual display color, and do not provide color preview or color editing; dynamic prefixes are also skipped.

- `fcolorbox` supports completion, hover, signature help, as well as preview and color editing of the two literal colors of the border and background. It supports sharing a model between the two or specifying a model separately; when sharing a grayscale model, changing one of them to color will fill in an independent background model and retain the actual color of the other.

- `cmyk` is converted to RGB preview according to the default rules of xcolor, and the color picking and editing retains the CMYK model; when the color does not change, the original four components and the black component are retained, and when the color is changed, the default black separation is used. The borders and backgrounds of a shared CMYK model can be edited separately, while the colors and components remain unchanged.

## Verbatim text and save name

The curly brace or character delimited codes of `\mintinline` and `\mint` are parsed and highlighted as verbatim text, retaining commands, labels and file examples within the code, supporting cross-line, Unicode delimiters and incremental editing; providing fragment and header signature help. See [minted code](minted.md) for boundary rules.

Skip `%` comments, `\verb`, `\lstinline`, and common verbatim environments (`verbatim`, `lstlisting`, `minted`, `comment`, and FancyVerb's) when parsing `Verbatim`, `LVerbatim`, `BVerbatim`, `SaveVerbatim`, `VerbatimOut` and their respective asterisk forms, and fvextra's `VerbatimWrite`, `VerbatimBuffer`). Example tags, commands, and file inclusions in a verbatim environment will not be entered into the source code index, and renaming retains the literal content; environment name completion, folding, verbatim highlighting, and unclosed environment repair are supported. Does not emulate execution behavior caused by `commandchars`, custom environments, or internal macros. FancyVerb only checks the first literal closing tag in each line; when closing tags from other environments appear first in the same line, subsequent tags with the same name will continue to be displayed, and the source code index will not be restored in advance. The content discarded by FancyVerb on the same line after the mark is closed will not participate in symbol indexing or editing; the next line resumes normal source code parsing, and the excess content error at the end of the line reported by the compiler will still remain. The options and saved names in the environment header are read according to parameter boundaries; the literal closing tag does not end the text, and multi-line options and comment continuations are supported. The two fvextra writing and buffering environments share FancyVerb's header, body, and end line rules and only support its native unstarred name. The saved name parameters of `UseVerb`, `UseVerbatim`, `LUseVerbatim`, `BUseVerbatim`, `UseMVerb`, and `pUseMVerb` are also processed as data, and the previous format options continue to be parsed normally. The inline text of `\SaveVerb{name}|text|`, `\SaveGVerb{name}|text|` and `\Verb|text|` is also processed literally, supporting asterisks, one-time optional parameters, comment continuation lines, grouping delimiters and Unicode delimiters; source code parsing is restored at the end of the line when the end delimiter is missing. Commands in `aftersave`, `formatcom` and other options are still indexed normally, and renaming retains the display text. When the text of `\\Verb` has been read by known macro parameters or macro definitions such as `\\textbf{...}`, the native behavior of FancyVerb is followed: ordinary control words continue to execute, tags, macro references and file inclusions in the text participate in indexing and renaming, and comments and grouping are processed according to ordinary TeX rules. Simple brace scope, zero-argument packaging, or macros that only read commands and delimiters will not enable this rule; the saved text of `SaveVerb` and `SaveGVerb` is still conservatively treated as data. Project-redefined FancyVerb commands are parsed as normal commands. When the current source file is explicitly loaded as `fvextra` or minted, `Verb` and `SaveVerb` use fvextra's verbatim parameter rules, supporting balanced braces and multi-line code; the default is to isolate code control words in macro parameters. `extra=false` can restore the original FancyVerb behavior, supporting calling options, `fvset`, `fvinlineset` and lexical grouping, and setting restoration in the ordinary LaTeX environment; package loading and setting expansion caused by other files or custom macros are not inferred for the time being.

The current file of `Verb` has purely static forwarding, stable command copying, and chain sharing corresponding text rules and header options. The alias still uses its own declaration and calling location to participate in navigation and renaming; the same-named command in the display code remains unchanged. Loops, unknown origins, later-than-copied definitions, parameterized wrappers, and ambiguous redefinitions are not inferred to built-in readers.

`\EscVerb[options]{code}` provides fvextra's escaped inline code support: the body reads balanced curly braces, escapes, and comments according to normal TeX rules, cross-lines are supported, the content is not indexed as an executable command, and `extra=false` does not change this isolation. Static copying and pure forwarding share read rules, and aliases retain their own navigation and renaming identities; syntax diagnostics are preserved and unfinished text is isolated when the closing curly brace is missing. Provides command snippets, hover and header option hints, and completion preserves existing code. Headers of direct source code follow fvextra special character look-ahead, and comments after optional parameters and in collected macro parameters are processed according to normal TeX rules.

fvextra's `VerbEnv` supports environment name completion, option prompts, folding and end name linkage editing, and only provides the native asterisk-free form. The header is read according to normal TeX's commenting and grouping rules until the active newline, then only one line of verbatim code is read, and the environment must be closed for the next line. Spaces and tabs are allowed before the closing tag and only spaces after it. When the closing line is invalid, the consumed code and the closing line are isolated, and the subsequent source code is restored to the index; the environment settings remain in the local scope until the subsequent actual closing command is restored. When a closing mark appears on the line of code itself, the recovery boundary of the native missing text error will be followed and the next line will not be swallowed.

FancyVerb's inline save and read commands, `fvset` and `fvinlineset`, provide command snippets, hover and header signature help. When completing an existing call, keep the verbatim code, bare name, and delimiter; when saving the name as data, you can still display signature help, and stop the prompt after completing the bare token, entering comments, or verbatim text. Call-level options terminate with the first unprotected closing bracket. The fvextra default reader supports `%` and backslash delimiters. Comments in ordinary parameters are still processed according to pretokenization rules; `extra=false` only retains these two special delimiters in pre-reading scenarios without optional parameters.

The options, name parameters and discarded tail of the first line of `lstlisting` are also processed according to the native boundary, and the literal closing mark that appears therein will not resume source code parsing in advance. Optional parameters support curly brace-protected right brackets, multi-line content, and comment continuation lines; ordinary newlines will end the option search. The exact `\end{lstlisting}` in the text ends the verbatim area. If the closing mark of other environments appears first on the same line, the search can still be continued; the LaTeX command after the real closing mark participates in navigation, renaming and file movement normally. Folding, highlighting, environment name linked editing and unclosed repair use the same boundary.

`\lstinline` supports paired delimiters and curly brace codes, and options and codes can contain blanks and comment continuation lines. `*` can be used directly as a delimiter; the curly brace form in ordinary text ends at the first literal `}`, and backslashes and percent signs in the code are treated as is. Restore source indexing at end-of-line when closing delimiter is missing, compiler end-of-line errors persist.

Macro parameters with known parameter syntax in the current source file and code in the macro definition body are bounded by pre-read TeX tokens: curly braces are paired normally, comments and escapes are still valid, delimiters can span lines, and nested grouping protects delimiters with the same name. This rule is maintained even when the outer known macro parameters or definition text have not been closed, and the diagnostics of missing closing brackets in the outer layer is retained; it is restored immediately after filling in the brackets. Supports copy macros, copy chains and purely static forwarding such as `\let` and `\NewCommandCopy` from stable sources; no inference will be made when the source is multiple declared, defined later than copied or the parameter syntax is unknown. Ordinary scope, grouping after zero-argument commands, and unknown parameter syntax still use ordinary text rules; just using the `\lstinline` control word itself as a parameter will not change the way subsequent code is read.

The code body does not participate in navigation, references, renaming, or file dependencies, and commands in the header options are still indexed normally. Purely static forwarding, stable command replication and its chaining that can be confirmed in the current source file also use the same code boundaries, alias declarations and real calls can still be navigated and renamed, and the same-named command in the example remains intact. The command provides completion fragment, hover and header option prompts; retains the original delimiters and codes when completing existing calls.

Saving text names supports definition jumps, quotes, hovers, completions and versioned renames. `SaveVerb` shares the name with `SaveVerbatim`, `UseVerb` and the three `UseVerbatim` commands read this group; `SaveGVerb` uses another group with `UseMVerb` and `pUseMVerb`. Names are matched according to their complete literal values, retaining leading and trailing spaces, commas, and Unicode; curly braces are automatically added when rewriting bare parameters. Modifications to shared files will cover all dependent projects, and each project will be checked for definition and naming conflicts. Empty names, macro expansions, comments within names, and cross-line names are not inferred; calls containing dynamic names, related redefinitions, executable character settings, `SaveMVerb` definitions that cannot be statically confirmed, or project ambiguities will prevent automatic renaming.

Ordinary macro references in dynamically saved names still support jump, reference query, hover, completion and macro renaming, such as `\UseVerb{\keyname}`; macro references with literals `\csname keyname\endcsname` and `\csuse{keyname}` are also recognized. Modifying the macro name will update these usage locations simultaneously, but the saved name value resulting from macro expansion will not be inferred. The name argument produces no LaTeX declarations, tags, or file dependencies; comments, verbatim text, `\detokenize{...}` content, and the next token of `\string` remain intact.

When the name parameter for `SaveVerb`, `SaveGVerb`, and each read command contains only a common macro, the compiler-confirmed undefined macro error pinpoints that command and provides a candidate versioned spelling fix within the project. Positioning checks both FancyVerb expansion frames and source code echoes; user macro wrappers, mixed names, extra expansion frames, and shortened echoes that cannot be uniquely matched continue to use full line diagnostics.

Known derived commands in the name parameter are associated with the corresponding symbols, for example `\theexercise`, literal `\csname c@exercise\endcsname` or `\csuse{theexercise}` are associated with counter `exercise`; navigation and renaming retain derived prefixes such as `the`, `c@`. The same applies to known derived commands for theorem environments, general environments, and conditional switches, and the shared item conflict check continues; base names in direct control words must still use TeX command letters.

Save `\arabic`, `\roman`, `\Roman`, `\alph`, `\Alph`, `\fnsymbol` and `\value` within the name It also tracks its static counter parameters and supports jump, reference, hover and renaming; the theorem counter continues to belong to the original environment, and the curly braces are automatically added when the bare parameters are renamed. Parameters are matched according to their complete literal values. Dynamic parameters and parameters containing semantic blanks are not inferred; annotations and literal conversion contents remain unchanged.

The grouping argument to these commands provides counter name completion, including built-in counters, project counters, and theorem counters; shared definitions go into candidates for their own projects, and the names of individual papers remain isolated. Selecting completion replaces the entire parameter content, with cross-line parameters using the main edit located on the request line and any additional edits necessary; support for name input that has not yet been closed.

Completion is also provided for a single bare ASCII counter parameter in the saved name, for example, `\arabic x` is completed to `\arabic{xlong}`; the curly braces are automatically completed during replacement, and only the parameter token is modified, and the subsequent name text, comments, and newlines are retained.

The contents of `\detokenize{...}` and the single token consumed by `\string` are not indexed as executable commands; the control sequence operands in macro declarations and command replication are still processed as commands. FancyVerb literal conversion wrappers in file names continue to support navigation, completion, signature help, and file renaming.


Direct calls to tags and citation keys, static named calls, and pure forward aliases share project explanations. After a built-in reference command is redefined by the user, its ordinary parameters will no longer provide key navigation/completion, nor will they be renamed with other real references. Confirmable static usage in the full macro body is still involved in editing; references with different meanings between parameter data, token operands, and shared consumers prevent partial renaming. Confirmed literal examples remain as is. Cumulative limit for a single interpretation is 32 MiB, 200,000 commands, 8,192 statements, 20,000 keys per source, and 100,000 cumulative key interpretations; partial renames are not returned when the index is truncated or exceeded.
