# Index and glossary processing

[Back to documentation](README.md) · [Compilation result analysis](build-analysis.md) · [Compilation configuration](build-configuration.md)

`analysis.requiredIndexTools` summarizes the indexing tools explicitly requested in the final TeX log. Two complete warning texts for rerunfilecheck are currently recognized:

- `Rerun LaTeX/makeindex to get index right.`
- `Rerun LaTeX/makeindex to get glossary right.`

Both report the lowercase tool name `makeindex`. The list is deduplicated and sorted; there is still only one item when the index and glossary change simultaneously. The request also sets `rerunRequired: true`, indicating that LaTeX needs to continue running after the tool has completed processing:

```json
{
  "rerunRequired": true,
  "requiredIndexTools": ["makeindex"],
  "requiredBibliographyTools": []
}
```

Indexing tools are aggregated independently from BibTeX/Biber and can appear in their respective lists at the same time. Without an explicit index request, `requiredIndexTools` is `[]`.

## Explicit compilation pipeline

`build.indexTools` defaults to an empty list. After configuration, `latex.build`, `latex.rebuild` and post-save compilation are all executed in the same background task: first run LaTeX to generate input, then process the index in the configuration order, and finally force LaTeX to read the results; when [documentation stage](bibliography-processing.md) is configured at the same time, the tool will run TeX twice. There is no need to guess tool parameters from logs or start concurrent processes independent of the compilation task.

Normal indexes can use the default makeindex settings:

```json
{
  "build": {
    "executable": "pdflatex",
    "indexTools": [{}]
  }
}
```

Glossaries can be configured together with normal indexes. For example, there is `glossary.ist` next to the main document, which declares `keyword "\\glossaryentry"`:

```json
{
  "build": {
    "executable": "pdflatex",
    "indexTools": [
      {},
      {
        "inputExtension": "glo",
        "outputExtension": "gls",
        "arguments": ["-s", "%r/glossary.ist", "-o", "%t", "-t", "%l", "%i"],
        "dependencies": ["glossary.ist"]
      }
    ]
  }
}
```

Settings for each task:

| Fields | Default values and meanings |
| --- | --- |
| `executable` | `makeindex`, directly call the executable file |
| `arguments` | `["-o", "%t", "-t", "%l", "%i"]`, complete parameter list, without shell |
| `inputExtension` / `outputExtension` | `idx` / `ind`; also supports `glo` / `gls`, `acn` / `acr`, `nlo` / `nls` |
| `jobName` | Use the actual compiled product name when not set; the naming index can be set to `people`, read `people.idx` and generate `people.ind` |
| `dependencies` | Additional input files such as styles, relative to the main documentation, or absolute paths can be used; up to 128 items |
| `timeoutSeconds` | 30 seconds per tool call, range 1–3600 |

The tool working directory is the actual product directory, consistent with `build.outputDirectory`, latexmkrc and `build.jobName`. `%i` is the relative file name of the current index input, `%t` is the relative file name of this temporary output, `%l` is the relative file name of the temporary processing log; `%r` is the main documentation, `%f` is the absolute path of the main file, `%o` is the product directory, and `%j` is the product name of the index task. Placeholders are only replaced once, spaces in the path or literal text such as `%j` will not be expanded again. The parameters must use `%i` and `%t`; makeindex must also use `-t %l` to specify a verifiable processing log.

Each call will atomically replace the formal index after confirming that the exit is successful, the input and additional dependencies have not changed, and the output is indeed generated. The original index of the task is retained when canceled, timed out, tool failed, or no output was produced. makeindex still returns exit code 0 after rejecting entries or style errors, so the server checks the new processing log separately; handling reject entries, style errors, diagnostic truncation, or missing full summaries fails. The new log is saved as `.ilg` / `.glg` / `.alg` / `.nlg`; when the tool fails, as long as the input and dependencies are still valid, this log is also saved for inspection. `processedIndexTools` in successful analysis provides input, output, and processing log URIs.

## Tool Diagnostics

Explicit makeindex tasks publish messages in the processing log as standard editor diagnostics, source `makeindex`:

| Diagnostic Codes | Level and Location |
| --- | --- |
| `invalid-index-entry` | Error, locate the actual input entry line generated by the current task `.idx` / `.glo` |
| `invalid-index-style` | Error, location log clearly points to the actual style file and line |
| `index-entry-warning` | Warning, for example, multiple encapsulation commands for the same key on the same page conflict, locate the entry line that generates the input |

Ranges use UTF-16 and support CRLF. When the file is unreadable, the line number is out of bounds, the log location is incomplete, or the input file does not match the task, the diagnostics falls back to the root document, and `unresolvedLocation` in the data is `true`; the source will not be guessed based on the file with the same name. `inputUri`, `transcriptUri`, `reportedFile` and `reportedLine` retain processing context. Compiling again after fixing will clear the old diagnostics.

The index input may be macro-expanded, and the line number of the generated entry cannot be directly regarded as the line number of `\\index` in `.tex`; currently targeted to the generated input or style file. Custom tools still retain standard output and failure details, and do not apply makeindex's logging syntax. Both log and source file reads are budgeted, and old indexes are not overwritten by processing results that cannot be fully verified.

If the index input is changed in the last pass of LaTeX, continue running the tool and LaTeX for up to four rounds; if it is still not stable, an error will be returned and the PDF containing the old index will not be reported as successful. `analysis.indexProcessingRounds` returns the actual processing round number. Empty index input/output is legal; compilation success will only be returned after confirming that the final PDF is valid. Logs and diagnoses are based on the last pass of TeX and the actual updated document processing logs of this pipeline. Temporary warnings from previous passes will not overwrite the final results.

All steps share the existing task ID, status, progress, `latex.cancelBuild`, shutdown server, and save check. Unsaved buffers on additional dependencies can prevent startup; modifying sources or file bindings during execution can cause results to expire, and style file events can cancel affected tasks. Two projects, even if they have different PDF names, cannot write to the same named index or processing log at the same time. Configure up to 32 tasks; duplicate output will be rejected.

`build.timeoutSeconds` limits each LaTeX call, with each indexing task using its own timeout. When using custom compilation `arguments`, you also need to explicitly configure `rebuildArguments` for forced LaTeX passes after processing; invalid configuration and missing style dependencies will report an error before the first compilation. Only open the corresponding task in projects that do have index input; missing input files will result in an error. The default latexmk may already handle normal indexing, explicit tasks are suitable for projects that require specifying additional steps or parameters.

## Manual processing

Ordinary indexes usually first generate `.idx` from LaTeX's `\makeindex` declaration and `\index` entry, then call a tool to generate `.ind`, and finally use `\printindex` of the `makeidx` package to sort it into PDF. For example, run in the product directory:

```sh
makeindex main.idx
```

Once the tool is complete, execute `latex.build` in the editor. The product directory and file name prefix depends on the `outputDirectory` and `jobName` configuration of the project.

The styles, input and output parameters required for the glossary are agreed upon by the project. For example, the `glossaryentry` data written by kernel `makeglossary` can use the corresponding style file `glossary.ist`:

```text
keyword "\\glossaryentry"
```

Then run:

```sh
makeindex -s glossary.ist -o main.gls main.glo
```

LaTeX documents also need to load the generated files. Other glossary packages may require different tools, styles, or processing steps and should be configured according to the corresponding package.

The quick fix menu provides `Rebuild …` when the current root document's `build.indexTools` can handle the actual input in the warning. Normal index requests must match the `idx` task; glossary requests must match the corresponding `glo`, `acn`, or `nlo` tasks. The file name must match the jobName of the task: the individual file name is parsed according to the actual product directory, the relative path containing the directory is parsed according to the main documentation, and the absolute path must correspond to the same product. The tools and parameters for configuring tasks are determined by the user, and the menu does not infer style parameters.

When there are no matching tasks, file types, or name inconsistencies, only the tool summary is retained; standalone tools can still be run manually. When the menu is executed, the current configuration, original diagnostics and document version are rechecked. Old operations after removing tasks or modifying the name/type will be rejected. Shared sources are checked separately for each root document that generates the diagnostics, and tasks from other projects are not borrowed.

## Log and update boundaries

Recognize the complete rerunfilecheck warning header, file name and request body, and support package continuation, 60 / 79 column wrapping and extra blank lines after full lines. Similar words in file names are not treated as real requests, and parentheses do not change the source of adjacent diagnostics. Similar text such as examples, incomplete requests, other tool names and error levels will not be entered into the tool list; simply writing `.idx` / `.glo` or missing files will not infer the required tools.

The list reflects explicit requests for this final log and is not used as a persistent to-do queue. rerunfilecheck can stop warnings when verifying that a file no longer changes, even if the user has not yet run makeindex; list clearing itself does not prove that the index has been processed. Console output from earlier rounds does not overwrite the final log. `latex/buildFinished` and `latex.buildStatus` use the same digest; cancellation, timeout, or expired results continue to return `analysis: null`.

When the diagnostic input is omitted, `truncated` is `true` and the tool list represents the observed request.

## verify

```sh
cargo test --locked --test index_workflow
cargo test --locked --lib index_diagnostics
cargo test --locked --test protocol index_processing_diagnostics
cargo test --locked --test protocol index_workflow
cargo test --locked --test index_workflow -- --include-ignored
cargo test --locked --test index_tools --test rebuild_actions
cargo test --locked --test protocol index_rebuild_actions
cargo test --locked --test protocol index_tool_analysis
cargo test --locked --test index_tools -- --include-ignored
```

Real regression requires pdfLaTeX, XeLaTeX, LuaLaTeX, makeindex, makeidx and rerunfilecheck. In the 60 / 79 column logs of the three engines, index and glossary requests are first generated, the execution tool generates `.ind` / `.gls` and compiles the PDF, then the entries are modified and the process is repeated to check the tool list, actual entries and the number of PDF pages.

Explicit pipeline regression additionally uses real pdfLaTeX / makeindex to verify only the first pass of index layout, glossary style, entry updates, final PDF, and location of rejected entries with exit code 0 in normal/quiet mode, zero exit style errors, and conflict warnings. Default tests cover atomic replacement, four-round caps, missing inputs, extra dependencies, symlinks, input changes, cancellation/timeouts, and child process cleanup; stdio covers state consistency, save checks, shared named index conflicts, expired results, and cleanup after diagnostic fixes.
